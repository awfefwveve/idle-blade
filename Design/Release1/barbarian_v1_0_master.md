### 0.2 제품 약속

플레이어는 “큰 바바리안이 작은 적 무리를 더 빠르고 넓게 쓸어버리는 변화”를 산다. 숫자만 증가하는 구간을 최소화하고, 무기 교체·새 스킬·광폭화 빈도·승급 외형을 성장의 증거로 보여준다. 수익 모델은 성장 기간과 수집 속도, 광고 시청, 외형에 대가를 받는다. 특정 보스를 결제 버튼으로 삭제하거나 유료 구매 여부에 따라 몬스터 난이도를 몰래 바꾸지 않는다.

## 1. 세계관과 플레이 목표

추방당한 전사가 타락한 선조에게 빼앗긴 부족의 불꽃을 되찾는 짧은 원정이다. 지역마다 한 문장의 목표와 보스 처치 후 두 문장의 사건을 제시한다. 이야기 때문에 자동사냥을 중단시키는 긴 대화는 넣지 않는다.

프롤로그: “부족의 불꽃이 꺼진 날, 너는 추방당했다. 선조의 힘을 되찾으려면 누구보다 강해져야 한다.” 첫 보스: “그룬은 쓰러졌다. 빼앗긴 무기가 다시 네 손에 돌아왔다.” 최종 보스: “카르둠의 분노가 흩어지고, 제단에 불꽃이 돌아왔다. 이제 너의 이름이 새로운 선조의 이름이다.” 완주 후: “원정 완료. 남은 시련과 장비 수집으로 전사의 기록을 완성하라.”

초단기 목표는 다음 강화와 다음 광폭화, 단기 목표는 보스 한 마리, 중기 목표는 새 스킬과 승급, 장기 목표는 본편 완주와 도감이다. 500 이후 미완성 스테이지를 숫자만 늘려 제공하지 않는다.

## 2. 전체 플레이 구조

앱 시작 → 인증·버전 확인 → 서버 시간·저장 상태 수신 → 미정산 전투 및 방치 보상 확인 → 자동사냥 → 강화 또는 장비 교체 → 보스 도전 → 스테이지·기능 해금 → 던전·승급·탑 → 종료 → 다음 접속.

재화는 일반사냥에서 쌓이고, 보스는 진행을 검증한다. 보스 실패는 진행도나 소지품을 잃는 사건이 아니라 현재 부족한 성장 방향을 알려주는 사건이다. 메뉴를 열어도 일반사냥은 진행한다. 도전 전투 중에는 장착·성장 스냅샷을 변경하지 못한다. 상품 수령은 가능하되 진행 중인 전투 능력치에는 반영하지 않는다.

### 2.1 메인 상태와 이동

`highest_cleared`는 최고 클리어 스테이지, `farm_stage`는 현재 사냥터다. 최초값은 각각 0과 1이다. 선택 가능한 사냥터는 1부터 `min(500, highest_cleared + 1)`까지다. 다음 미클리어 스테이지에서만 보스 게이지가 증가한다. 이미 깬 낮은 사냥터에서는 골드·재료를 얻지만 다음 보스의 게이지는 증가하지 않는다.

1스테이지는 15마리, 2~10은 25마리, 11~500은 40마리를 처치하면 해당 보스 도전 자격이 열린다. 처치 수는 중복 정산하지 않고 서버가 기록한다. 한 번 자격을 얻으면 실패 후에도 유지된다. 해당 보스를 처치하면 다음 스테이지로 이동하고 게이지를 0으로 만든다. 자동 도전은 기본 OFF, 첫 보스 성공 후 안내하며 사용자가 켤 수 있다. 자동 도전 상태에서 한 번 실패하면 자동으로 OFF로 바뀐다.

일반사냥에서 사망하면 3초 뒤 최대 체력, 분노 0으로 부활한다. 골드·장비 손실은 없다. 120초 안에 3회 사망하면 낮은 사냥터를 추천한다. 사용자가 ‘안정 사냥 자동 이동’을 켠 경우에만 서버가 직전 검증된 안정 사냥터로 변경한다. 숨겨진 난이도 보정은 하지 않는다.

## 3. 전투 규칙

### 3.1 공간과 자동 행동

보이는 화면은 가로형 2D 횡스크롤이다. 1.0의 실제 전투 좌표는 **X축 한 줄**이다. 몬스터를 Y축으로 몇 픽셀 어긋나게 그려 군단처럼 보이게 하지만, 이 Y 오프셋은 판정·이동·사거리에 영향을 주지 않는다. 점프 높이도 연출이다. 다중 레인이나 상하 회피를 나중에 끼워 넣지 않는다.

논리 좌표는 1유닛=1000mm 정수, 기본 이동속도는 주인공 3200mm/초다. 타깃은 살아 있는 가장 가까운 적, 동률이면 낮은 `entity_id`다. 공격 사거리에 들어오면 이동을 멈추며, 타깃이 죽거나 사거리 밖으로 나가면 다시 탐색한다. 바라보는 방향은 타깃 방향이다. 기본공격의 전방 범위는 무기별 거리까지이며, 대상 수 상한에 도달하면 거리·ID 순서로 선택한다. 회전베기 등 주변형 스킬은 전후방을 함께 타격한다.

몬스터는 주인공의 좌우 바깥에서 생성되고 자동 접근한다. 원거리형은 사거리에서 정지한다. 적끼리 물리적으로 밀어내지 않는다. 겹침을 피하기 위한 시각적 분산만 허용한다. 일반 몬스터 최대 40마리, 초당 생성 상한 6마리다. 최대치에 도달하면 생성 타이머를 넘겨 적립하지 않는다.

### 3.2 프레임과 우선순위

논리 전투는 50ms, 초당 20틱이다. 렌더링은 30/60fps다. 물리 엔진, 애니메이션 이벤트, `Time.timeScale`, 실시간 화면 흔들림을 피해 판정의 근거로 쓰지 않는다. 틱 순서는 만료 처리 → 소환·생성 → 타깃·이동 → 스킬 예약 → 평타 예약 → 피해 이벤트 정렬 → 동시 피해 적용 → 사망 처리 → 처치 보상·분노 → 회복 → 종료 판정이다. 같은 틱의 유효 공격은 함께 적용한다. 주인공과 보스가 같은 틱에 죽으면 실패다. 제한시간 마지막 틱에 보스만 죽으면 성공이다.

스킬은 준비된 전쟁함성 우선, 나머지는 슬롯 1→2→3 순서다. 스킬 시전 시작 후 공통 시전 잠금은 250ms다. 이미 시작된 다단히트는 별도 이벤트로 남는다. 시전 중이어도 이동 가능 여부는 스킬별 규칙을 따른다. 주인공이 죽으면 남은 주인공 공격 이벤트와 출혈을 제거한다. 일반공격은 시전 잠금 중 예약되지 않으며, 평타 충전치는 1회분까지만 쌓인다.

쿨다운은 시전 시작 시부터 계산한다. 유효 타깃이 없는 공격 스킬은 사용하지 않는다. 전쟁함성은 전투 중이며 6초 버프가 없을 때 사용한다. 스킬 범위 밖이면 우선 평타 타깃을 향해 이동한다. 도약강타·돌진만 자체 접근을 수행한다. 자동 전투의 스킬 타이밍을 유저가 직접 눌러 조절하는 기능은 1.0에 없다.

### 3.3 피해와 회복

계산 단위 `bp`는 10000=100%다. 피해 공식은 다음과 같다.

`피해 = max(1, floor(공격력 × 타격계수 × [1 + 해당 피해 보너스 합] × 치명배율 × 광폭 피해배율 × [1 - 대상 피해감소]))`

공격력 가산 보너스는 한 버킷에서 합친다. 일반공격·스킬 피해는 각 유형 버킷에서 합치고, 보스 상대라면 보스 피해 보너스를 그 유형 버킷에 추가한다. 광폭 피해배율은 별도 곱이다. 같은 이름 버프는 중첩하지 않고 종료시각만 갱신한다. 계산은 마지막에 한 번 내림한다. 중간 곱셈 오버플로를 검사한다.

치명타는 기본 5%, 피해배율 150%다. 한 평타 또는 하나의 스킬 타격 이벤트마다 한 번 뽑고, 그 이벤트의 모든 대상에 같은 결과를 적용한다. 출혈은 치명타·흡혈·추가 분노를 발생시키지 않는다. 빗맞음·회피·속성 상성·관통·속성 저항은 1.0에 없다.

흡혈은 실제 적용된 직접 피해를 기준으로 한다. 죽은 적의 잔여 HP를 넘어선 피해는 제외한다. 한 이벤트 회복량은 최대 HP의 2%, 1초 누적은 최대 HP의 5%까지다. 일반 회복과 전쟁함성 회복은 흡혈 제한과 별개이며, 항상 최대 HP까지만 회복한다. 보스에게 경직·넉백·도발은 적용하지 않는다.

### 3.4 능력치 상한

| 능력 | 상한 |
|---|---|
| 평상시 공격속도 | 초당 3.5회 |
| 광폭화 공격속도 | 초당 5회 |
| 치명타 확률 | 80% |
| 치명타 피해배율 | 500% |
| 피해 감소 | 60% |
| 쿨다운 감소 | 40% |
| 흡혈 계수 | 10%, 실제 초당 회복은 별도 상한 |
| 광폭 지속시간 | 10초 |

스탯 상세창에 기본값·보너스·상한·현재 적용값을 구분한다. 상한 초과분을 몰래 다른 스탯으로 전환하지 않는다. 상한 초과 상태를 알려 주며, 장기 성장은 공격력·HP·스킬 계수·수집으로 이어진다.

## 4. 기본 강화와 수치 구조

공격력·HP 레벨은 0부터 3000, 공격속도는 100, 치명확률은 150, 치명피해는 200, 생명회복은 100까지다. 모든 레벨업은 확정 성공한다. 강화 버튼은 +1, +10, 최대를 제공한다. ‘최대’는 실제로 구매 가능한 누적 비용을 서버가 구해 한 명령으로 처리하며 클라이언트가 1000개 RPC를 보내지 않는다. 불가능하면 부족 재화와 다음 1회 비용을 보여 준다.

`기본 공격력(L)=floor((25+2L)×1.001^L)` / `기본 HP(L)=floor((250+20L)×1.001^L)`

`공격력 다음 강화비(L)=ceil(15×1.008^L)` / `HP 다음 강화비(L)=ceil(10×1.008^L)`

공격속도는 레벨당 +0.5%p, 치명확률은 +0.2%p, 치명피해는 +1%p, 생명회복은 초당 최대 HP의 +0.01%p다. 각각 비용과 해금 조건은 `stat_upgrades` 표를 따른다. 수식은 빌드 시 표로 전개한다. 실제 전투에서 양 언어의 부동소수점 `pow()` 결과를 비교하지 않는다.

최종 공격력은 기본 공격력 × 무기 등급 배율 × (1 + 무기 슬롯 강화레벨×1%) × 승급 배율 × (1 + 공격력 가산 보너스)다. 전쟁함성 +25%는 공격력 가산 보너스 버킷에 들어간다. HP는 기본 HP × [1 + 장착 방어구 3개의 HP 보너스 합] × 승급 배율 × [1 + HP 가산 보너스]다. 각 방어구의 HP 보너스에는 해당 슬롯 강화 배율 `(1 + 레벨×0.5%)`을 적용한다.

표시 전투력은 추천용이다. `CP=floor(평균 단일대상 DPS 추정×10 + 최대HP×0.1)`로 표시하되 서버가 보스 성공을 CP 비교로 결정하지 않는다. 평균 DPS 추정은 60초 표준 허수아비 시뮬레이션에서 얻는다. ‘권장 전투력’은 참고이며 장착 조합에 따라 결과가 다를 수 있다고 표시한다.

## 5. 분노와 광폭화

분노 최대는 100, 적을 한 번 이상 맞힌 기본공격 행동당 8을 얻는다. 여러 적을 동시에 맞히거나 치명타가 발생했다고 배수로 얻지 않는다. 광폭 중에는 분노를 얻지 않는다. 100에 도달한 틱의 공격 처리가 끝나면 광폭에 들어가며, 최초 상태 기준 6초 동안 공격속도 +35%, 사거리 +50%, 타깃 상한 +4, 피해 +25%를 적용한다. 종료 후 2초간 분노 획득이 멈춘다. 다음 사이클은 0에서 시작한다.

주인공 몸집은 약 1.2배가 되되 판정 크기는 바꾸지 않는다. 픽셀을 흐리게 늘리지 않도록 광폭 외곽 실루엣·팔·무기 궤적용 프레임을 추가한다. 보스 전용 HP 바와 플레이어 위치가 가려질 만큼 화면을 채우지 않는다. 시작 순간 0.05초 이내의 시각적 멈춤과 저음 효과를 주되 서버 시간은 그대로 흐른다.

승급전마다 특성 포인트 1개, 최대 5개를 얻는다. 특성은 3갈래, 갈래마다 4개가 직렬 선행 관계다. 각 노드에 1포인트, 중복 투자 불가다. A는 광폭 공격, B는 생존, C는 분노 빈도다. 초기화는 무료이고 사냥 정산 경계에서 적용한다. 도전 중 변경은 금지한다. 목록과 정확한 수치는 `talents` 표를 따른다.

A3 충격파는 광폭 중 세 번째 유효 평타마다 주변 최대 8명에게 공격력 50% 피해를 주며, 치명·흡혈·분노·다른 발동 효과를 일으키지 않는다. B4는 도전 한 번당 최초 치명상을 HP 1로 막고 1초간 피해 무효화한다. 일반사냥에서는 60초 재사용 대기다. C3 처치 분노는 비광폭·비잠금 상태에서 초당 최대 5회만 적용한다. C4의 시작 분노 20은 보스·던전·탑·승급 진입에만 적용한다.

초반 광폭 가동률 25~35%, 성장 후 50~65%를 튜닝 목표로 삼는다. 이는 검증된 결과가 아니라 측정 후 맞출 목표다. 항상 광폭인 상태를 1.0의 필수 종착점으로 만들지 않는다.

## 6. 무기·방어구·중복 처리

도끼는 800ms에 계수 100%, 사거리 1600mm, 기본 3명. 대검은 1100ms에 140%, 2200mm, 5명. 망치는 1600ms에 200%, 1800mm, 4명이다. 망치의 세 번째 평타는 일반몹에 0.2초 경직을 준다. 스킬 피해는 무기 평타 계수가 아니라 최종 공격력을 사용한다. 세 계열의 기본 단일대상 지속피해를 비슷하게 두고 사거리·분노 속도·경직을 구분한다.

등급은 일반·고급·희귀·영웅·전설·신화의 6단계다. 배율은 1.0/1.65/2.7/4.4/7.2/12.0이다. 각 아이템은 최초 획득 시 영구 사용권을 얻고, 이후 획득분은 중복 수량으로 보관한다. 영구 사용권은 합성·분해로 사라지지 않는다. 같은 아이템의 **중복 5개**를 소비하면 같은 계열 다음 등급 1개를 확정 획득한다. ‘총 보유 5개’와 혼동되지 않게 사용권과 중복 수량을 UI에서 분리한다.

무기 강화는 개별 아이템이 아니라 **무기 슬롯**에 귀속된다. 방어구는 투구·갑옷·장화 슬롯 각각에 강화레벨이 있다. 바꾸거나 합성해도 투자 재료를 잃지 않는다. 강화 상한은 슬롯마다 200이다. 무기 강화 1회 비용은 현재 레벨 e에서 광석 `5+2e`, 골드 `ceil(100×1.035^e)`다. 방어구 슬롯은 광석 `3+e`, 골드 `ceil(80×1.035^e)`다. 실패·파괴·강화 이전권은 없다.

방어구는 랜덤 옵션과 테마 세트를 넣지 않고 **등급 세트**만 사용한다. 세 슬롯이 모두 고급 이상이면 최대 HP +5%, 모두 영웅 이상이면 HP +10%와 피해감소 +3%p, 모두 신화면 HP +15%와 피해감소 +5%p다. 세 효과를 중첩하지 않고 가장 높은 한 개만 적용한다. 방어구 외형은 주인공 기본 실루엣을 해치지 않는 투구·어깨·부츠 레이어로 표현한다.

합성 일괄 버튼은 잠금 중복을 제외하고 낮은 등급부터 처리한다. 한 명령 최대 200회 합성, 초과는 다음 명령으로 분리한다. 실제 결과와 소모를 서버가 미리 계산하고 확인창에 표시한다. 확인용 견적은 버전이 달라지면 갱신한다. 장착 사용권을 소비할 수 없으므로 강제로 벗기는 처리는 없다. 중복 잠금은 아이템별 ‘최소 남길 중복 수량’으로 관리한다.

분해는 중복만 가능하고 일반/고급/희귀/영웅/전설/신화 각각 광석 1/3/10/30/100/300개를 준다. 신화의 다음 등급은 없으며 중복은 보유하거나 분해한다. 신화 초월·무한 각성은 추가하지 않는다. 영웅 이상 분해에는 등급·수량을 표시한 확인창을 한 번 더 사용한다. 자동 분해는 1.0에서 제외한다.

## 7. 스킬 시스템

스킬 8개는 모두 메인 진행으로 확정 해금한다. 소환에서만 나오는 전용 스킬은 없다. 스킬 소환은 8종의 강화 조각을 얻는 방법이다. 아직 해금하지 않은 스킬 조각도 보유할 수 있으나 사용할 수 없고, 소환 화면에서 해금 스테이지를 명확히 표시한다.

첫 슬롯은 3, 두 번째는 8, 세 번째는 20스테이지 클리어로 열린다. 장착 프리셋은 사냥용·보스용 2개, 무료다. 같은 스킬을 여러 슬롯에 넣지 못한다. 장착 변경은 사냥 정산 후 반영하며 기존 스킬의 남은 쿨다운은 계속 흐른다. 새 장착 스킬은 해당 스킬의 기본 쿨다운을 부여해 교체로 연속 발사하는 행동을 막는다. 도전 시작은 전체 쿨다운 0에서 시작한다.

해금 시 레벨 1이다. 현재 레벨 L에서 다음 레벨 비용은 해당 조각 `1+floor((L-1)/5)`개, 스킬 가루 `20×L²`개다. 최대 30레벨이며 공격 스킬은 계수에 `(1+0.03×(L-1))`을 곱한다. 전쟁함성은 레벨당 공격력 보너스 +0.5%p만 증가하고 회복량·지속시간은 유지한다. 출혈은 시전 시 공격력 스냅샷과 레벨 계수를 사용한다. 출혈은 적별 1개이며 재적용 시 피해가 더 큰 것을 택하고 남은 시간은 6초로 갱신한다.

최고레벨 스킬 조각은 1개당 가루 10개로 수동 교환할 수 있다. 모든 스킬이 최고레벨이면 보석을 쓰는 스킬 소환은 차단하고 남은 티켓의 전환 가치를 안내한다. 스킬 조각에는 합성 확률·랜덤 승급을 넣지 않는다.

첫 기본 사냥 조합은 회전베기+도약강타+지면분쇄, 보스 조합은 전쟁함성+투척도끼+피의참격이다. 이는 시작 추천이며 정답을 강제하는 보너스 세트는 없다. 각 스킬의 타격·범위·쿨다운은 `skills` 표가 기준이다.

## 8. 승급·유물·도감

승급은 추방자 → 전사 → 광전사 → 부족영웅 → 전쟁군주 → 선조의화신이다. 메인 20/60/120/220/350을 클리어하면 다음 승급전이 열린다. 입장 재화는 없고 실패도 무료다. 45초 안에 시험 보스를 처치한다. 시험 보스는 해당 해금 스테이지 보스 HP의 1.25배, 공격력 1.2배를 사용하며 지역 패턴을 유지한다. 성공 시 공격력·HP 승급 배율, 외형, 특성 포인트를 같은 트랜잭션으로 적용한다. 배율은 누적 곱이 아니라 해당 등급의 1.0/1.5/2.3/3.6/5.8/9.5 중 한 값이다.

유물은 메인 30에서 열린다. 유물 조각 100개로 원하는 유물 하나를 제작해 레벨 1을 얻는다. 현재 L에서 다음 레벨은 조각 `10+5L`개다. 최대 50, 실패 없음, 랜덤 제작 없음. 유물 효과는 보유 즉시 계정에 적용한다. 12종 모두 공격력만 올리지 않고 일반공격·스킬·보스·HP·치명·흡혈·분노·골드로 분산한다. 전체 효과는 같은 버킷에서 합산하고 상한을 적용한다.

도감은 재화 소모 없이 최초 등록한다. 무기는 등급별 0.1/0.2/0.3/0.5/0.8/1.2% 공격력, 방어구는 같은 값의 HP를 영구 가산한다. 스킬 최초 해금은 각각 스킬 피해 +0.5%. 몬스터 각 100마리 처치는 골드 +0.2%, 지역 완주는 각각 HP +1%다. 등록 보너스는 같은 계열끼리 합산한다. 영구 사용권 체계이므로 합성·분해 후에도 도감이 사라지지 않는다. 색칠만 된 동일 몬스터 변종을 새 도감 항목으로 중복 계산하지 않는다.

## 9. 콘텐츠 상세

### 9.1 메인과 보스

일반 몬스터 기준 HP=`round_half_up(55×1.026^(s-1))`, 공격력=`round_half_up(8×1.022^(s-1))`, 기본 골드=`round_half_up(5×1.03^(s-1))`다. 실제 몬스터는 유형별 HP·공격·골드 배율을 적용한다. 보스 HP는 일반 기준 HP의 45배, 10의 배수 스테이지는 60배다. 보스 공격은 일반 기준 공격의 6배, 기본 공격 주기는 2초다. 보스 피해감소는 지역별 0/5/10/15/20%다.

보스 전투는 30초, 최대 HP·분노 0(특성 적용 가능)·스킬 준비 상태에서 시작한다. 실패 시 보스 남은 HP 비율, 생존 시간, 평균 DPS, 사망/시간초과 이유를 보여 준다. ‘공격력 강화’, ‘방어구 강화’, ‘스킬 편성’ 가운데 관련된 두 개만 추천한다. 결제 팝업으로 직접 연결하지 않는다. 이미 깬 보스의 반복 연습에는 진행·보석·최초 보상을 주지 않는다.

최초 클리어 보상은 보석 20개, 10의 배수는 보석 100개다(20+100이 아니라 100으로 대체). 골드는 해당 스테이지 기준 골드의 50배다. 30 이상 10의 배수는 유물 조각 25개를 추가한다. 메인 최초 보상은 스테이지 ID 기준 한 번이다.

지역: 핏빛초원 1~100, 검은숲 101~200, 잿불광산 201~300, 얼음무덤 301~400, 선조의폐허 401~500. 각 지역의 세 몬스터는 55/25/20% 가중치다. 보스 소환몹은 골드·분노 처치 특성·도감·퀘스트 보상을 모두 0으로 한다. 소환몹을 이용한 무한 재화/분노 농사를 차단한다.

### 9.2 골드 던전

10스테이지 클리어에 열린다. 50단계, n단계 해금은 메인 `10n` 클리어다. 해당 기준 스테이지의 일반 HP 75%, 공격력 75%인 적 30마리를 45초 안에 처치한다. 생성은 초당 3마리, 최대 20마리다. 보상은 해당 스테이지 기준 골드의 3600배다. 최대 단계는 500 기준이며 보상이 현재 임의 장착 조합에 따라 변하지 않는다.

### 9.3 장비 던전

15스테이지 클리어에 열린다. n단계 해금은 메인 `max(15,10n)` 클리어다. 기준 스테이지 `10n` 보스 HP·공격의 75%인 보스를 45초 안에 처치한다. 보상은 광석 `30+10n`, 스킬 가루 `20+5n`, 무기 티켓 1장, 방어구 티켓 1장이다. 추가 랜덤 장비 드롭은 넣지 않는다.

두 던전은 종류별 매일 기본 2회, 광고로 +1회까지다. 일일 횟수는 한국 시각 오전 5시에 초기화되고 미사용 기본 횟수는 이월되지 않는다. 도전 시작 시 횟수를 예약하고 성공 확정 시 소비한다. 실패·명시적 포기는 예약을 반환한다. 접속 종료만으로 포기 처리하지 않고 서버 결과로 확정한다. 최초 성공한 단계는 이후 무료 소탕이 가능하고 동일 보상을 준다. 유료 소탕권은 없다.

### 9.4 시련의 탑

25스테이지 클리어에 열린다. 100층, 입장 무제한, 최초 보상만 지급한다. f층은 기준 메인 스테이지 `min(500,5f)`의 보스 HP·공격의 80%를 사용하고 시간은 45초다. 5층 주기로 기본 / 소환몹 2 / 피해감소 +10%p / 일반공격 피해감소 20% / 스킬 피해감소 20%를 순환한다. 보스 기본 패턴에 층 보정을 추가하되 전체 피해감소는 60%를 넘지 않는다.

층당 보석 50, 유물 조각 10, 5의 배수 층은 유물 조각 50을 추가한다. 주간 초기화·시즌 초기화는 없다. 재도전은 무료 연습이며 보상 없음. 100층 완료 후 기록과 성공 조합을 볼 수 있다.

### 9.5 완주 후

500스테이지 클리어에서 마지막 스토리와 무료 ‘선조의 왕좌’ 프로필 프레임을 지급한다. 메인 버튼은 ‘원정 완료’로 바뀌고 최고 사냥터에서 파밍한다. 남은 탑·승급·유물·장비·도감을 진행할 수 있다. 모든 성장까지 끝났다면 미완성 시스템을 암시하는 알림을 띄우지 않는다. 1.0만으로도 목표를 달성한 게임으로 마무리한다.

## 10. 첫 30분과 초보자 보호

시간은 플레이테스트 목표이며 스크립트가 시간을 재서 유저를 기다리게 하지 않는다. 실제 해금은 서버에서 확인한 진행 상태를 따른다.

| 구간 | 목표 체험 | 조건·확정 지급 |
|---|---|---|
| 0~3분 | 자동 접근, 첫 강화, 첫 광폭 | 기본 일반 도끼·일반 갑옷, 골드 100; 공격력 강화 3회 안내 |
| 3~7분 | 첫 보스와 무기 변화 | 1스테이지 클리어 시 고급 도끼 1개 확정 |
| 7~12분 | 회전베기로 군집 처치 | 3스테이지 클리어 시 S01 사용권과 스킬 가루 100 |
| 12~20분 | 두 스킬 조합·던전 | 8클리어 S02·슬롯2, 10클리어 골드 던전 |
| 20~30분 | 승급·외형·목표 | 15클리어 S03, 20클리어 첫 승급전·슬롯3·S04 |

메인 2클리어 시 무기 티켓 10장을 주고 무료 10회 소환을 체험한다. 튜토리얼 소환도 일반 공개 확률과 같은 추첨이며, 고급 도끼 확정 지급은 퀘스트 보상으로 분리한다. 희귀 확정인 것처럼 연출하고 실제 뽑기라고 주장하지 않는다.

튜토리얼 스텝은 서버 단위 상태이며 앱을 종료해도 해당 조건에서 이어진다. 목표가 이미 충족돼 있으면 재수행시키지 않는다. 설명은 한 번에 한 문장과 한 타깃, 3스테이지 이후 건너뛰기 가능, 보상 차이는 없다. 첫 보스 실패는 정상 안내를 제공하되 실제 체력 수치를 몰래 낮추지 않는다. 첫 보스와 첫 광폭을 보기 전에는 광고·상품 팝업이 없다. 최초 상품 안내는 3스테이지 클리어 뒤 상점 배지 하나로 끝낸다.

초보 7일 미션은 날짜 출석 강제가 아니라 단계별 체크리스트다. 당일 해금만 제한하고 기한 만료는 없다. 목표 순서는 메인 5/20/40/60/100/150/200, 던전·승급·스킬 조합이며 각각의 총 보상을 명시한다. 모든 핵심 스킬은 이 이벤트 없이도 메인 해금으로 얻는다.

## 11. 일일·주간 반복 구조

일일 활동은 6가지, 각 20점이며 100점이면 보석 200개와 스킬 가루 100개를 받는다. 항목은 접속, 일반몹 300마리, 골드 던전 1회, 장비 던전 1회, 성장 행동 3회, 도전 1회다. 광고·결제·소환을 필수 항목으로 넣지 않는다. 장비 던전이 아직 잠긴 계정은 해당 항목을 ‘메인 보스 1회’로 대체한다. 성장 행동은 실제 강화·제작·스킬 레벨업만 세고, 모든 성장 상한 도달 계정은 ‘일반몹 300마리 추가’로 대체한다. 이미 완주한 계정의 도전은 연습 전투도 인정한다. 각 치환은 일일 키 생성 시 고정해 도중 중복 계산하지 않는다.

주간은 일일 100점 보상을 서로 다른 5일에 수령하면 보석 700개, 유물 조각 100개를 준다. 월요일 오전 5시 초기화다. 출석은 연속 강요 없는 7회 순환으로 보석 20/20/30/30/30/30/50을 지급하고 마지막은 무기 티켓 10장을 추가한다. 결석해도 1일차로 되돌리지 않는다.

안정적인 무료 반복 보석 공급은 일일 200 + 주간 평균 100 + 출석 평균 30 = 일평균 330개다. 이는 모든 조건을 충족하는 경우의 설계상 평균이며 메인·탑·성장 패스·초보 미션·우편은 별도 일회성이다. 소환은 종류별 무료 1회/일도 제공하고 동일 확률·천장에 포함한다. 광고 수익을 얻지 못해도 이 기본 공급을 깎지 않는다.

## 12. 방치 보상과 재화

기본 방치 누적 상한은 12시간, 효율은 검증된 기준 사냥 속도의 70%다. 월정액·광고 제거로 상한을 차별화하지 않는다. 기준 속도는 저장된 사냥터·장착 스냅샷으로 서버가 표준 120초 전투를 시뮬레이션해 분당 골드·몬스터별 처치·재료율을 얻는다. 같은 빌드 해시는 캐시한다. 죽음과 접근 시간도 반영하며 단순 `공격력×시간`을 쓰지 않는다. 표준 샘플의 첫 30초는 준비 구간, 뒤 90초만 측정한다.

적 보상 기준의 일반사냥 추가 재료는 유효 처치 50회당 광석 1개, 100회당 스킬 가루 1개다. 몬스터 보상 가중치와 무관한 실제 처치 수를 사용하며 잔여 카운터를 보존한다. 방치에서는 몬스터별 정수 카운터와 소수 잔여량을 서버가 함께 보존해 짧게 자주 받는 행동으로 이익이 생기지 않게 한다. 방치 처치는 도감과 일반 처치 미션에 반영하지만 다음 보스 자격 게이지·스테이지 클리어에는 반영하지 않는다.

방치 보상은 재접속 시 기본분을 자동 확정한 뒤 영수증 형태로 보여 준다. 최소 30분 누적 영수증에 한해 광고 또는 광고 제거 혜택으로 기본 보상의 50%를 한 번 더 받을 수 있고 하루 2회다. 추가분에는 재화·재료만 포함하고 이미 반영한 처치 수를 복제하지 않는다. 한 영수증에 한 번만, 24시간 안에 선택 가능하다. 받지 않아도 기본분을 잃지 않는다.

| 재화 | 주요 획득 | 소비·성격 |
|---|---|---|
| 골드 | 사냥·방치·골드 던전·최초 보상 | 기본 능력·슬롯 강화; 정수 대용량 |
| 유료/무료 보석 | 구매/콘텐츠 보상 | 같은 구매력, 회계상 분리; 무료분 우선 소비 |
| 광석 | 사냥·장비 던전·중복 분해 | 무기·방어구 슬롯 강화 |
| 스킬 가루 | 사냥·장비 던전·활동·조각 전환 | 스킬 강화 |
| 유물 조각 | 탑·메인·주간 활동 | 선택 제작·강화 |
| 소환 티켓 3종 | 퀘스트·던전·패키지 | 해당 배너 1회, 보석보다 우선 사용 |
| 일일 던전 횟수 | 서버 일일 키 | 해당 던전 성공·소탕 시 차감 |

무료 보석과 유료 보석에 능력·확률 차이는 없다. 획득한 유료 화폐는 유효기간을 두지 않는다. 티켓+보석 혼합 결제는 소환 전 정확한 차감 내역을 표시한다. 10회 소환은 1회×10이며 할인이나 별도 확정 슬롯이 없다. 보유 수량·재료 보관함에는 판매 목적의 확장 한도를 넣지 않는다.

## 13. 소환 확률·천장·원장

무기·방어구 소환은 1회 보석 100개다. 등급 확률은 일반 50%, 고급 28%, 희귀 15%, 영웅 5.5%, 전설 1.4%, 신화 0.1%로 합계 100%다. 등급을 뽑은 뒤 무기는 세 계열, 방어구는 세 슬롯을 각각 동일 확률로 뽑는다. UI는 전체 등급 확률과 등급 내 아이템 조건부 확률을 분리해 보이며 개별 아이템의 전체 확률도 표시한다. 1/3 때문에 화면의 반올림 합계가 미세하게 달라질 수 있음을 설명하고 서버는 정수 가중치/균등 추첨을 사용한다.

무기·방어구 배너는 **각각 전설 이상 미획득 199회 후 다음 1회 보장**이다. 한 번의 추첨에서 먼저 일반 확률로 결과를 뽑는다. 직전 실패 카운터가 199이고 결과가 전설 미만이면 전설로 바꾼다. 전설 이상이면 카운터 0, 아니면 +1이다. 따라서 보장 회차는 전설 99.9%, 신화 0.1%다. 200번마다 추가 상자를 주는 방식이 아니다. 10회 소환은 이 규칙을 1→10 순서대로 적용한다. 무료·티켓·보석 소환이 동일 천장을 공유하며 기간 만료가 없다. 숨은 소프트 천장은 없다.

스킬 소환은 1회 보석 200개, 각 스킬 조각 묶음 12.5%, 한 묶음 5개다. 모두 같은 수량이라 별도 등급·천장은 없다. 원하는 조각이 나오지 않을 수 있다는 점과 전체 목록을 구매 전에 보여 준다. 첫 스킬 사용권은 메인에서 확정 지급되므로 소환이 기능 해금의 유일한 경로가 아니다.

모든 소환에는 배너 버전, 표시 확률 버전, 이전/이후 천장, 사용 티켓·유료·무료 보석, 결과 목록, 요청 ID, 서버 시각을 기록한다. 구매 가능 화면과 실제 추첨 테이블이 다르면 소환을 중단한다. 개인별 구매 이력·국가·과금 성향에 따라 같은 배너 확률을 바꾸지 않는다. 공개 확률은 앱과 서비스 웹 안내에 함께 게시하는 설계로 한다. 국내 적용 범위·표시 방식·변경 공지는 최신 법령과 심의·법률 검토를 거친다. [S09, S13]

## 14. 상점과 과금

아래 금액은 한국 출시용 **기획상 목표 가격**이며 실제 스토어 가격과 세금·지역 가격 등급은 상품 등록에서 확인한다. 앱 표시 가격은 스토어 SDK가 반환한 현지화 문자열을 사용한다. 원화 숫자를 코드에 박아 넣지 않는다. 수익이나 구매 전환을 보장하는 가정은 없다.

| 30일 보급권 | 5,900원 | 유료 보석 300 즉시 + 30회 무료 보석 100; 자동 갱신 없음 |

광고 제거는 배너별·던전별·버프별 상품으로 쪼개지 않는다. 나중에 보상 광고 위치를 추가하더라도 통합 제거 권한이 적용되도록 설계한다. ‘광고 제거’와 ‘무한 보상’은 다르다는 설명을 구매 창에 적는다. 제거 구매 후에는 광고 SDK를 로드할 필요 없이 동일 보상 RPC를 권한 검증으로 호출한다.

30일 보급권은 자동 결제 구독이 아니라 기간제 소모성 상품이다. 구매 시 첫 100개가 발생하고 이후 24시간마다 100개씩, 총 30회 발생한다. 로그인하지 않아도 지급 권리가 누적되며 이미 발생한 보석 수령권은 사라지지 않는다. 서버가 마지막 수령 회차를 저장한다. 기간 중 재구매는 막아 중첩·연장 규칙을 줄인다. 복원은 게임 계정 원장과 스토어 구매 내역을 근거로 지원한다.

성장 패스 목표는 메인 10/20/40/60/80/100/130/160/200/250/300/350/400/450/500이다. 각 목표에서 무료 트랙은 무료 보석 50, 유료 트랙은 무료 보석 200+무기 티켓 5를 지급한다. 기간은 영구이며 시즌 초기화가 없다. 상점에는 미리 달성한 항목, 총 지급량, 아직 미달성인 목표를 구분한다.

상점 자동 팝업은 최초 1회 설명을 제외하고 쓰지 않는다. 보스 실패 후 결제 압박 카운트다운, 실제로 끝나지 않는 할인, 결제 금액에 따른 비밀 난이도, 미성년자 성향 기반 과금 유도는 넣지 않는다. 상점에서 다음 성장 목표와 구매로 얻는 구체적 수량을 보여 주되, ‘이 상품이면 반드시 보스 성공’이라고 보장하지 않는다.

## 15. 보상 광고

하루 최대 7회: 방치 추가 2회, 사냥 골드 버프 3회, 골드 던전 추가 1회, 장비 던전 추가 1회다. 사냥 버프는 30분 골드 +20%이며 공격력은 올리지 않는다. 재사용 시 최대 90분까지 시간을 연장하고 수치를 중첩하지 않는다. 서버 UTC 타임스탬프가 만료를 결정하며 방치 구간은 버프가 실제 유효했던 시간만 +20%를 반영한다.

광고 시청 전 보상과 일일 잔여 횟수를 표시한다. 강제 전면 광고·강제 앱 시작 광고는 없다. 광고 재고 없음은 상품 구매 유도 팝업이 아니라 “지금 준비된 광고가 없습니다”로 끝낸다. 광고 시작 전 `nonce`와 보상 컨텍스트를 서버에서 예약한다. 광고 SDK 완료 이벤트만으로 재화를 주지 않고 광고 제공사의 서버 서명 검증 콜백을 확인한다. 콜백이 늦으면 보상을 ‘확인 중’으로 표시하고 재접속·재시도에서도 같은 광고 트랜잭션으로 수령을 이어 간다. [S10]

첫 공급사는 AdMob 보상형을 기준으로 어댑터를 만든다. 미디에이션 다중 공급사와 복잡한 입찰 최적화는 1.0 이후다. 광고 SDK 버전·개인정보 동의·추적 동의·국가별 노출 가능 여부는 출시 게이트다. 광고의 +20% 골드는 경제 모델에서 별도 시나리오로 측정한다.

## 16. 화면과 사용자 경험

### 16.1 메인 화면

화면 위쪽은 스테이지·프로필·전투력, 골드·보석·설정. 중앙 60% 안팎은 전투와 HP/분노. 왼쪽은 다음 목표 카드 1개, 오른쪽은 보스 게이지/도전 버튼. 하단은 장착 스킬 3개와 5개 내비게이션(성장/장비/스킬/도전/상점)이다. 전투 화면 자체가 홈이며 별도 마을 씬을 만들지 않는다.

일반 메뉴는 화면 오른쪽 최대 48% 패널로 열어 왼쪽 전투를 계속 볼 수 있다. 상세 확률·우편·상점 결제 확인은 중앙 모달이 가능하다. 모달은 1개만 열며 뒤에 모달을 계속 쌓지 않는다. 장비 세부 비교에는 현재/변경 후 공격력, 사거리, 타깃 수, 기본공격 주기, 광폭 예상 빈도를 보여 준다. 전투력 숫자 하나만으로 장착을 결정하지 않도록 한다.

상점·광고 배지는 빨간색 알림으로 남발하지 않는다. 빨간 점은 무료로 즉시 수령할 수 있는 보상이나 실제 가능한 강화에만 사용하며, ‘광고를 보면 받을 수 있음’은 다른 표시로 구분한다. 모든 버튼은 비활성 이유를 보여 준다. 보유 화폐가 최신이 아니면 구매 버튼을 잠깐 잠그고 먼저 정산한다.

뒤로가기 규칙은 최상위 모달 닫기 → 패널 닫기 → 메인에서 종료 확인이다. 상점 구매 중 시스템 창을 강제로 닫지 않는다. 서버 응답 대기는 버튼 단위 표시를 우선하고, 전체 화면 잠금은 초기 로드·정합성 복구에만 사용한다. 10초 이상이면 설명과 재시도 버튼을 제시한다.

글자는 선명한 일반 한글 UI 글꼴, 전투 그림만 픽셀 아트로 한다. 실제 폰에서 최소 터치 목표 48dp 상당을 확보하며 긴 숫자·번역·20:9 노치·태블릿을 테스트한다. 피해 숫자 합산, 화면 흔들림·번쩍임 끄기, 진동 끄기, 절전 30fps, 좌우 도전 버튼 위치 교환 옵션을 제공한다. 기본 화면 흔들림은 약하게, 전면 섬광은 사용하지 않는다.

## 17. 픽셀 아트 제작 명세

‘촘촘함’은 픽셀 수를 무한정 늘린다는 뜻보다 근육·무기 실루엣·명암을 명확히 한다는 방향으로 정의한다. 기준 월드 렌더는 640×360, PPU 32, 타일 32×32다. 화면 비율이 넓어지면 수평 가시 폭을 늘리고 필수 UI는 안전영역에 고정한다. UI는 별도 네이티브 해상도 캔버스로 그린다. 무조건 640×360으로 UI까지 뭉개지 않는다.

주인공 기본 프레임 캔버스 80×80, 실제 몸체 높이 약 56~64px, 무기 포함 최대 바운드 112×96. 일반몹 32×32 또는 48×48, 보스 128×128, 아이콘 32×32다. 작은 적과 주인공은 1:2 정도의 크기 대비를 만든다. 광폭 전용 바운드는 128×112 안으로 제한한다. 광폭 시 UI 영역을 넘어가는 무기 이펙트는 클리핑한다.

주인공 애니메이션: 대기 4, 달리기 6, 평타 3계열 각 6, 피격 2, 사망 6, 함성 6, 도약 6, 착지 4, 승리 4프레임을 기본으로 한다. 스킬별 회전·돌진 동작은 기존 몸체 프레임과 전용 궤적을 조합하되 평타 3종의 자세 차이는 유지한다. 프레임당 손잡이 소켓 좌표를 데이터로 기록하고, 무기 레이어를 소켓에 맞춘다. 그림과 충돌 판정의 출처를 혼합하지 않는다.

색상은 흙색·회색 배경, 따뜻한 피부, 주황/빨강 광폭, 명확한 희귀도 테두리로 정리한다. 등급은 색만 아니라 테두리 장식과 이름으로 구분한다. 근육은 3~4단 명암, 외곽선은 어두운 유채색 1px, 광원은 좌상단으로 통일한다. 드롭 아이콘은 화면을 가리는 수십 개의 물리 오브젝트 대신 0.6초 흡수 연출 후 HUD 수치에 합친다.

Sprite는 Point 필터와 일관된 PPU를 사용하고 Pixel Perfect 카메라를 검증한다. 원본 픽셀 아트의 압축·아틀라스 가장자리 번짐·mipmap 여부는 기기별로 확인한다. 작은 핵심 시트는 무압축 우선, 메모리를 이유로 압축할 때는 실제 외곽선 품질을 확인한다. 해당 기능은 Unity 공식 Pixel Perfect 문서를 참고하되 문서에 나온 특정 패키지 버전이 Unity 6.3의 모든 조합에서 검증되었다고 가정하지 않는다. [S11]

아트 제작 순서는 주인공 기본 1세트·도끼1·군집몹1·보스1·초원1 → 광폭·회전베기 → 나머지 무기와 몬스터 → 지역 확장 → 등급 외형 → UI·상품 외형이다. 초반 전투가 재미없는데 18개 무기 외형부터 완성하지 않는다.

## 18. 사운드·연출

음악은 메인 사냥 5지역 각 1루프, 공용 보스 1, 공용 결과 짧은 스팅 2, 타이틀 1을 목표로 한다. 타격은 도끼·대검·망치 각 최소 3변형, 몬스터 피격 3군, 스킬8, 광폭 시작/종료, 강화·합성·승급·획득·버튼·오류 효과음을 준비한다. 동일 타격음 재생은 50ms 이내 중복을 합치고, 한 번에 최대 16개 월드 음원을 둔다.

광폭 시작은 저음 포효+무기 궤적 확장, 승급은 몸체 실루엣 노출+오라 변화, 무기 교체는 전투 복귀 후 첫 평타를 강조한다. 소환 연출은 10회 묶음 결과를 한 번에 확인할 수 있고 즉시 건너뛸 수 있다. 건너뛰기는 결과나 확률을 바꾸지 않는다. 희귀도 최고 연출은 최초 획득 때 길게, 중복은 짧게 하며 최고 길이 5초를 넘기지 않는다.

## 19. 운영·고객지원·계정

게스트 시작을 제공하고 Google/Apple 계정 연동을 지원한다. 게스트 계정은 앱 데이터 삭제 시 분실될 수 있음을 알린다. 첫 결제 전 계정 연동을 권유하지만 이용 조건·스토어 정책 검토 없이 강제로 계정을 새로 만들게 하지 않는다. 두 진행 계정을 자동 병합하지 않고 보존할 계정을 명시적으로 선택하거나 고객지원으로 보낸다. 원래 계정의 결제 영수증이 다른 계정에 재사용되지 않게 한다.

앱 내 계정 삭제 진입점, 구매 복원, 문의 복사 정보(계정 ID·앱 버전·요청 ID), 약관·개인정보 링크를 제공한다. 삭제 요청 시 철회 절차·삭제 범위·법적으로 보관해야 할 거래 내역의 분리를 안내한다. 실제 보관 기간은 서비스 지역의 최신 법률 검토로 정한다. Apple의 계정 삭제·복원·확률 안내 요구도 출시 검수에 포함한다. [S09]

우편은 공지성·보상성으로 구분하고 보상은 서버가 수령 상태와 같이 확정한다. 일반 무료 운영 우편은 30일 보관을 기본으로 하되 구매한 상품·보석·이미 발생한 유료 지급 권리를 만료 우편으로만 전달하지 않는다. 미수령 구매 보상은 구매 원장에서 복구할 수 있어야 한다. 보상 우편 삭제는 수령 후에만 허용한다.

운영 명령은 점검 공지, 최소 버전, 상품/소환/광고 중지, 개별 우편, 한정 대상 보상, 계정 조회, 거래 조회, 차단·해제다. 재화 직접 수정은 운영자 권한과 사유를 요구하고 원장에 남긴다. 대규모 지급은 사전 합계 검토와 승인 절차를 둔다. 실제 결제 승인과 계정 데이터 변경이 일치하지 않을 때는 운영 복구 큐를 사용한다.

## 20. 측정 지표와 밸런스 승인

필수 행동 이벤트는 튜토리얼 스텝, 첫 강화·광폭·무기 교체·보스 성공, 스테이지 진입/실패, 스킬 편성, 던전 성공/소탕, 방치 수령, 소환, 광고 요청/검증/지급, 구매 시작/검증/지급/환불, 세션 종료다. 재화 관련 이벤트는 서버가 확정한 값으로 기록한다. 개인정보·원문 영수증·인증 토큰을 분석 이벤트로 보내지 않는다.

잔존율·매출 목표 수치는 업계 평균으로 단정하지 않는다. 내부 초기 가설은 첫 세션 3분 내 광폭 경험 90% 이상, 튜토리얼 완료 70% 이상, D1 35%·D7 12% 이상, 충돌 없는 세션 99.5% 이상이다. 이 값들은 프로젝트의 목표이고 보장이나 비교 가능한 시장 통계가 아니다. 유저 획득 비용을 쓰기 전에 실제 표본·코호트·광고비·스토어 수수료·서버비를 넣어 순기여를 계산한다.

밸런스는 무결제·광고만·광고 제거+보급권·성장 패스 구매·고액 소환의 시나리오를 분리한다. 무결제도 모든 기능을 해금하고 본편을 완료할 경로가 있어야 한다. 구매 시나리오가 콘텐츠를 수분 만에 끝내면 가격이 아니라 수급·성장 상한·콘텐츠 분량을 함께 조정한다. 목표 진행 구간은 30분 메인20/첫승급, 1일 메인40~60, 7일 메인120~180, 30일 메인300 전후, 45~75일 본편 완주를 우선 가설로 한다. 현재 초기 곡선이 이 속도를 달성한다는 검증은 아직 없으며, 실제 시뮬레이터와 플레이테스트로 맞추는 것이 출시 필수 작업이다.

## 21. 이번 버전에서 하지 않을 것

# 바바리안 키우기 — Unity / Nakama / PostgreSQL 기술설계

버전 1.0.0-seed.1. 게임 규칙은 `01_게임기획서.md`, 실제 초기 테이블은 `data/`를 따른다. 이 문서는 구현 명세이며 해당 서버와 Unity 클라이언트가 이미 구현·실행 검증되었다는 의미가 아니다.

## 1. 고정 스택과 책임 경계

| 계층 | 선택 | 책임 |
|---|---|---|
| 클라이언트 | Unity 6.3 LTS / C# | 입력·UI·전투 예측·픽셀 연출·캐시·스토어 SDK |
| 렌더/UI | URP 2D / uGUI / TextMeshPro | 2D 스프라이트·안전영역·가상화 목록 |
| 서버 | Nakama / Go 런타임 | 인증 후 게임 명령·전투 검증·경제·권한·시간 |
| 데이터베이스 | PostgreSQL | Nakama 사용자·Storage·Wallet·구매 검증 기록 |

Unity 6.3 LTS 계열을 유지한다. 정확한 에디터 패치, URP·Input System·Addressables·IAP·Nakama Unity SDK·광고 SDK는 첫 기술 검증에서 한 조합으로 잠그고 `ProjectVersion.txt`, `manifest.json`, `packages-lock.json`, 서버 이미지 digest에 남긴다. 현재 설치된 패치가 주어지지 않았으므로 임의의 Unity 패치 번호를 확정했다고 주장하지 않는다. 공식 안내상 Unity 6.3은 LTS 계열이다. [S01]

Nakama 공식 Docker 예시에 등장하는 3.37.0과 PostgreSQL 16 계열을 초기 호환성 검증 기준으로 삼되, 보안 패치와 지원 상태를 확인한 정확한 이미지를 고정한다. `latest` 태그를 운영에서 사용하지 않는다. Go 플러그인은 서버와 동일 태그의 pluginbuilder에서 빌드하고 플랫폼·Go·공유 의존성을 맞춘다. PostgreSQL을 사용자 지정 엔진으로 대체하거나 CockroachDB용 compose를 그대로 복사하지 않는다. [S02, S05, S12]

**서버가 소유하는 값:** 재화, 중복 수량, 강화 레벨, 장착, 특성, 보스 결과, 최고 스테이지, 방치 시간, 드롭, 소환 결과, 천장, 일일 횟수, 우편 수령, 구매·광고 권한. **클라이언트가 소유하는 값:** 화면 배치, 효과음, 진동, 카메라, 예측 표시, 환경설정 중 비경제 항목. 클라이언트는 `획득 골드=...`, `피해량=...`, `보스 성공=true`를 권한 있는 결과로 보내지 않는다.

## 2. 서버 구조: 상시 실시간 방이 아닌 명령형 검증

```text
Unity UI / CombatView
      │ 사용자 명령, build_version, request_id, expected_revision
      ▼ HTTPS
Nakama 인증 세션 → RPC 검증 → 계정 상태 읽기 → 순수 Go 도메인 계산
      │                             │
      │                       서버 전투 시뮬레이터
      ▼                             ▼
Storage 조건부 쓰기 + Wallet 변경 + 중복처리 영수증 + 원장
      │ 한 트랜잭션
      ▼
PostgreSQL
```

솔로 자동사냥을 위해 유저마다 Nakama 실시간 Match를 24시간 유지하지 않는다. 일반사냥은 10초마다 RPC로 정산하고 서버가 저장한 전투 상태에서 경과 구간을 재실행한다. 보스·던전·탑·승급은 시작 명령 때 고정 스냅샷과 시드로 제한시간 전체를 빠르게 계산하고 결과를 서버에 저장한다. 결과 공개와 보상 확정은 실제 서버 시간이 결과 도달 시각을 지났을 때만 가능하다.

WebSocket은 1.0 필수 의존성이 아니다. 우편 배지·공지 버전은 heartbeat 응답에 작은 변경 플래그로 실어 보낸다. 채팅·매칭·친구·실시간 협동을 위해 소켓을 유지하지 않는다. 시작 규모는 Nakama 노드 1개와 PostgreSQL 운영 인스턴스로 검증한다. 노드를 늘리는 것만으로 모든 Nakama 기능이 자동 분산·고가용성화된다고 가정하지 않는다. 장애조치·다중 노드의 구체 지원은 도입 버전·배포 방식 검증 후 별도 설계한다.

## 3. Unity 프로젝트 구성

```text
Assets/_Game/
  Bootstrap/             # 앱 시작, 서비스 수명, 환경 선택
  Domain/                # 순수 C# 스탯·전투·타깃·고정소수점
  Application/           # 명령 큐, 상태 store, 화면 use case
  Infrastructure/
    Nakama/              # SDK 래퍼, 인증, RPC DTO
    IAP/                 # StoreKit/GooglePlay 어댑터
    Ads/                 # AdMob 어댑터
    Persistence/         # 보안 토큰·비권한 캐시
    Content/             # 버전·해시·테이블 로더
  Presentation/
    Combat/ UI/ Audio/ VFX/
  Content/               # 생성된 읽기 전용 JSON, 에셋 카탈로그
  Art/ Sprites/ Animations/ Prefabs/
  Tests/EditMode/ Tests/PlayMode/
Packages/manifest.json
ProjectSettings/ProjectVersion.txt
```

씬은 `Bootstrap`과 `Game` 두 개로 시작한다. Bootstrap은 환경·인증·버전·데이터를 로드한 뒤 Game을 연다. Game 안에서 사냥·보스·던전의 전투 컨텍스트만 바꾸고 씬을 매번 새로 로드하지 않는다. 패널은 프리팹과 명시적인 화면 스택으로 관리한다. 모든 싱글턴이 서로 호출하는 구조, 범용 게임매니저 하나에 경제·전투·UI를 몰아 넣는 구조는 피한다.

asmdef는 Domain, Application, Infrastructure, Presentation, Editor, Tests를 분리한다. Domain은 UnityEngine 참조 없이 실행 가능하게 한다. 전투 로직은 MonoBehaviour의 Update에 직접 넣지 않고 `CombatSimulation.Step()`에서 진행한다. MonoBehaviour는 상태를 읽어 이동 보간·프레임 선택·효과음을 재생한다. 애니메이션 이벤트는 소리나 먼지 표시만 요청할 수 있다.

입력은 Input System, UI는 uGUI+TMP로 통일한다. ECS/DOTS, 복잡한 DI 프레임워크, 범용 행동트리, 원격 코드 다운로드는 1.0에서 도입하지 않는다. Addressables는 지역·UI 에셋 묶음과 메모리 관리에 사용하고 초기 필수 에셋은 앱에 포함한다. 원격 에셋이 실패하면 공지·보상 데이터만으로 앱이 진행 불가가 되지 않도록 필수 캐시를 둔다.

## 4. 순수 전투 시뮬레이터 계약

### 4.1 입력·출력

입력은 `simulation_version`, `content_version`, `combat_seed`, `combat_mode`, `stage_or_floor`, `build_snapshot`, `initial_state`, `max_ticks`다. snapshot에는 최종 스탯과 원본 장착 ID·레벨·특성·패시브를 함께 넣고 hash를 만든다. 서버는 DB에서 snapshot을 만들며 클라이언트가 보낸 최종 스탯을 복사하지 않는다.

출력은 terminal tick, 결과 코드, 남은 HP, 몬스터별 확정 처치 수, 생성 보상 원인, 전투 상태 hash, 요약 피해 통계다. 일반사냥은 다음 틱으로 이어갈 상태를 반환하고 도전은 결과만 확정한다. 서버와 클라이언트가 같은 콘텐츠·시드·초기 상태로 동일한 결과를 만들도록 한다. 보스 성공 판정의 유일한 권위는 서버다.

### 4.2 숫자와 결정성

위치는 mm 정수, 시간은 틱 또는 Unix milliseconds, 비율은 bp 정수, 분노는 1000=1점이다. HP·피해·재화는 64bit 정수로 저장하고 곱셈 중간 값은 checked 연산 또는 Go `math/big.Int` / C# `BigInteger` 보조 계산으로 보호한다. JSON의 경제 수량은 10진 문자열로 전달한다. 1.0 골드 상한은 9,000,000,000,000,000, 보석 합계 상한은 1,000,000,000이다. 오버플로는 조용히 감싸거나 음수로 바꾸지 않고 명령을 거절한 뒤 보상 복구 기록을 남긴다.

공격속도는 `aps_milli`로 계산한다. 틱마다 공격 누적기에 `aps_milli`를 더하고 20000 이상일 때 평타 1회분을 소비한다. 공격할 수 없는 동안은 최대 20000까지만 보관한다. 스킬 시전 잠금 중 누적은 유지하되 발사하지 않는다. 실제 APS는 무기 기본 주기와 공격속도 가산, 광폭 보너스를 적용한 뒤 상태별 상한으로 자른다. 스킬 쿨다운은 `ceil(base_cd_ms × (10000-cdr_bp)/10000/50)`틱이다.

시뮬레이션용 PRNG는 명시된 xorshift32(unsigned 32bit, zero seed 금지; <<13, >>17, <<5 순서)를 양쪽에 구현한다. 제한 구간 정수 추첨은 rejection sampling으로 편향을 없앤다. 엔티티 순회는 ID 오름차순, 같은 거리 타깃도 ID 오름차순이다. 해시맵의 순회 순서를 게임 로직에 사용하지 않는다. 동일 틱 이벤트 순서는 `tick, event_priority, caster_id, cast_sequence, hit_index, target_id`다. 치명 추첨은 피해 이벤트 단위이며 대상 수에 따라 RNG 소비 횟수가 달라지지 않는다.

유료 소환·보상 추첨은 이 PRNG를 쓰지 않는다. 별도의 서버 비밀키 기반 추첨 또는 암호학적 난수원을 사용한다. 클라이언트에 소환 RNG 시드·비밀키를 전달하지 않는다.

### 4.3 공유 테스트

단일 대상 60초, 범위 공격 40명, 다단히트 중 사망, 광폭 직전/직후, 공격속도 상한, 출혈 갱신, 쿨다운 상한, 흡혈 상한, 동시 사망, 제한시간 마지막 틱, 보스 소환, 프리셋 변경의 고정 벡터를 만든다. Go가 생성한 결과를 C# 테스트가 읽고 반대 방향도 확인한다. 최소 10,000개 고정 seed/build/콘텐츠 조합의 끝 상태와 reward hash가 일치해야 출시 후보가 된다. 이 테스트는 패키지에 실제 게임 시뮬레이터가 없으므로 현재 실행 완료된 것으로 표시하지 않는다.

## 5. 일반사냥과 방치 정산 알고리즘

`farm_state`는 전투 상태, `settled_through_ms`, `online_lease_until_ms`, `build_hash`, `content_version`, 누적 소수 나머지, 현재 사냥터를 보유한다. 현재 활성 클라이언트는 10초마다 heartbeat를 보내며 정상 처리 시 온라인 lease를 서버 현재시각+30초로 연장한다. foreground 여부는 편의 힌트일 뿐 보상 권한의 증거가 아니다. 허용된 온라인 속도로 자동사냥 요청을 계속 보내는 봇을 이 구조만으로 완전히 막는다고 주장하지 않는다. 시간 가속과 임의 결과 조작을 막는 것이 1차 목적이다.

정산 단계:

1. 서버 now를 읽고 마지막 정산보다 작으면 해당 경과를 0으로 처리하며 시간 경고를 남긴다.
2. 마지막 정산부터 `min(now, 기존 online_lease_until)`까지는 저장된 상태에서 20Hz로 재실행한다. 정상 heartbeat 사이에는 10초, 단절 시 최대 30초 구간이다.
3. lease 이후 now까지는 오프라인 구간이다. 연속 부재 세션에서 최대 12시간만 70% 기준율을 적용한다. 실제 전체 경과는 모두 소비해 다음 접속에서 상한 초과분이 다시 지급되지 않게 한다.
4. 오프라인 샘플 기준율은 저장된 빌드·사냥터·콘텐츠 버전에서 얻는다. 기준율은 골드 버프 없는 값으로 저장하고 버프 유효 구간을 시간 분할해 골드만 보정한다.
5. 골드·재료·몬스터별 처치의 나머지를 정수 분자/고정 분모로 보관한다. 청구를 잘게 나눈다고 올림 보상을 여러 번 받지 못한다.
6. 모든 지급, 카운터, 미정산 커서, operation receipt를 하나의 트랜잭션으로 저장한다.

bootstrap·강화·장착·특성·사냥터 변경은 먼저 이전 상태를 해당 서버시각까지 정산한 뒤 새 빌드를 적용한다. 새 스탯으로 과거 12시간 보상을 역산하지 않는다. 새로 얻은 아이템·구매 혜택이 과거 시간에 소급해 효율을 올리지 않는다. 강제 종료 직전 마지막 30초가 온라인으로 잡힐 수 있는 것은 명시적 lease 유예이며 중복 보상이 아니다.

오프라인의 몬스터별 처치 수는 경제/도감 카운터용 추정 집계이며 스테이지 해금에 쓰지 않는다. 오프라인 보상 화면은 ‘방치 효율 70% 기준’으로 설명한다. 오프라인 기간에 앱 업데이트가 발생하면 해당 기간의 기존 콘텐츠 버전을 보존해 정산하고 이후 최신 버전을 적용한다. 보존할 수 없는 장애 상황에는 공지된 마이그레이션 보상으로 처리하며 임의의 새 비싼 사냥터를 소급 적용하지 않는다.

## 6. 보스·던전·탑·승급 공통 도전 계약

`challenge_start`는 종류·대상 ID·프리셋 ID만 받는다. 서버가 해금, 입장 예약, active challenge 없음, 빌드 버전을 확인한다. 일반사냥을 start_at까지 정산하고 빌드·시드·최대 시간·콘텐츠 버전을 고정한다. 서버가 전체 전투를 시뮬레이션해 private result와 `terminal_at`을 저장한다. 클라이언트에는 challenge_id, seed, snapshot, 적 정의, start_at, 공개용 state hash만 보낸다. 성공 결과는 아직 공개하지 않는다.

도전 중에는 게임 내 성장·장착 명령을 `CHALLENGE_ACTIVE`로 거절한다. 구매가 외부에서 완료되면 아이템 지급은 허용하지만 active snapshot은 바꾸지 않는다. 일반사냥 재화는 도전 구간에 동시에 발생하지 않는다.

`challenge_finish`는 challenge_id만 받는다. now가 terminal_at 미만이면 `CHALLENGE_NOT_READY`와 남은 서버 시간을 준다. 클라이언트 승리 플래그·피해량·경과시간은 사용하지 않는다. now가 terminal_at 이상이면 저장된 결과에 따라 최초 보상·진행·횟수 소비/예약 반환을 한 번에 확정한다. 앱이 꺼졌더라도 다음 bootstrap에서 같은 처리를 수행한다. 전투 종료 후 다시 접속할 때까지의 시간은 terminal_at 이후 오프라인 사냥으로 취급한다. 승리 후 다음 스테이지 전투의 자동 도전은 앱 미접속 중 실행하지 않는다.

명시적 포기 명령은 terminal_at 전에만 유효하고, 실패 처리·던전 예약 반환·사냥 복귀를 서버 트랜잭션으로 적용한다. 이미 terminal_at이 지나 성공이 확정 가능한 상태에서 포기로 입장 횟수를 돌려받지 못한다. 같은 계정의 도전은 1개, 휘발성 메모리가 아닌 Storage에 기록한다. 서버 재시작 후에도 결과가 유지된다. 다음 전투부터 새 테이블을 쓰더라도 진행 중 전투는 고정 버전을 끝까지 사용한다.

## 7. Nakama 데이터 모델

Nakama의 인증·사용자·Storage·Wallet·검증 API를 사용한다. Unity가 PostgreSQL에 연결하거나 Nakama 내부 테이블을 직접 UPDATE하는 경로는 없다. 프로젝트 데이터를 담기 위해 Nakama 스키마 안에 별도 게임 테이블을 임의로 생성하지 않는다. 논리 엔티티는 Storage 컬렉션과 JSON으로 구성한다. 분석 내보내기가 필요하면 원장/outbox를 별도 파이프라인으로 읽는다. [S03, S04, S06]

## 8. 경제 트랜잭션과 동시성

모든 경제 명령은 다음 형태를 따른다. 코드는 실제 고정한 `nakama-common/runtime` 서명을 기준으로 구현하며 문서의 의사코드를 SDK 호출 그대로 복사하지 않는다.

```text
authenticate session context
validate payload, app/content version, operation type
read operation(request_id)
  exists + same hash -> previous response
  exists + different hash -> REQUEST_ID_REUSED
read player_meta + required state + wallet
check expected_revision and active_device_epoch
settle pending farm/challenge when permitted
compute costs, grants, counters, next state
validate non-negative counts, caps, all invariants
atomic commit:
  conditional player_meta write using read storage version
  conditional domain object writes
  wallet deltas with ledger enabled
  create-only operation receipt
  source-specific permanent claim marker
return committed revision and state delta
```

Nakama Storage 버전 조건과 MultiUpdate를 사용해 관련 Storage·Wallet을 함께 변경한다. wallet 차감과 아이템 추가를 별개의 호출로 순차 실행하지 않는다. 새 receipt·claim marker는 create-only 조건, 기존 상태는 읽어온 버전 조건을 사용한다. 모든 유저 경제 명령에 player_meta CAS를 포함해 서로 다른 컬렉션을 수정하는 명령끼리도 계정 단위 순서를 보장한다. [S04]

클라이언트는 경제 명령 큐를 하나로 직렬화한다. heartbeat와 버튼 명령도 같은 큐로 지나가며 현재 revision을 사용한다. 서버 CAS가 최종 방어선이다. 충돌 시 최대 3회 내부 재읽기·재계산하거나 `STATE_STALE`를 반환한다. 무한 재시도하지 않는다. ‘최대 강화’의 결과 수량이 바뀔 수 있는 재견적은 사용자에게 보여 준다. 고정 수량 소환은 동일 비용·동일 요청 해시로만 재시도한다.

일반 request receipt는 7일 뒤 정리할 수 있다. 오래된 요청은 expected_revision 불일치로 다시 적용되지 않아야 한다. 구매·광고·최초 보상·우편의 고유 지급 마커는 각 데이터의 보존 정책에 따라 유지해 일반 요청 캐시 삭제와 독립적으로 재지급을 막는다. 결제 증빙 보존 기간은 법률 검토 대상이며 무료 요청 캐시 TTL과 혼동하지 않는다.

외부 결제 API나 광고 서버 호출은 DB 트랜잭션 안에서 오래 기다리지 않는다. 외부 검증 단계와 실제 보상 지급 단계를 영속 상태로 연결한다. 네트워크에서 exactly-once 전송을 보장한다고 표현하지 않는다. 최소 한 번 전송될 수 있는 상황에서 **게임 내 효과가 한 번만 적용**되도록 설계한다.

## 9. RPC 계약

모든 요청 공통: `request_id(UUID)`, `client_build`, `content_version`, `expected_revision`, `device_epoch`, `payload`. bootstrap은 초기 revision이 없을 수 있으므로 별도 초기 동기화 계약을 사용한다. 인증된 user ID는 Nakama context에서 읽으며 body의 user_id는 허용하지 않는다.

응답 공통: `ok`, `code`, `server_time_ms`, `state_revision`, `content_version`, `delta`, `result`, `retryable`. 실제 Nakama 오류 코드와 게임 코드 매핑을 한 곳에 둔다. 응답 성공을 저장하기 전 UI가 확정 보상을 표시하지 않는다. 이 목록은 별도 `rpc_contracts` 표에도 들어간다.

추천 오류는 AUTH_REQUIRED, VERSION_REQUIRED, CONTENT_MISMATCH, STATE_STALE, REQUEST_ID_REUSED, INSUFFICIENT_FUNDS, LIMIT_REACHED, LOCKED, CHALLENGE_ACTIVE, CHALLENGE_NOT_READY, ALREADY_CLAIMED, AD_PENDING, PURCHASE_PENDING, ECONOMY_OVERFLOW, RATE_LIMITED, MAINTENANCE다. 비밀번호·내부 SQL 오류·stack trace를 사용자 응답에 노출하지 않는다.

요청은 일반 JSON 최대 32KB, 영수증은 검증된 상한 내 별도 제한, 일괄 처리 최대 100아이템/10소환/200합성이다. 정상 클릭+heartbeat를 방해하지 않는 토큰 버킷으로 계정·IP rate limit를 분리한다. 운영 키를 앱에 넣어 클라이언트가 관리자 RPC를 호출하게 하지 않는다.

## 10. 결제: 검증과 지급을 분리

Unity IAP의 구매 대기 콜백 → 서버 검증 → grant record/Wallet/권한의 원자 지급 → 클라이언트에 확정 응답 → 스토어 구매 완료 처리 순서다. PENDING·취소·실패는 지급하지 않는다. 스토어가 준 product ID·구매 계정·앱 ID·거래 ID·구매 상태를 확인한다. 상품 가격·보상 번들은 서버 catalog에서 읽고 클라이언트가 전달한 지급량을 사용하지 않는다. [S07, S08]

Google은 purchase token을 서버로 보내 공식 검증 경로를 사용한다. Apple StoreKit 2+Unity IAP 5.x 조합은 기존 Base64 receipt 경로와 다르므로 JWS를 받는 경로를 구현한다. Nakama 공식 문서에서 StoreKit 2 지원 기준은 3.37.0 이상으로 안내되어 있다. Unity IAP 버전별 pending order와 confirm API는 실제 고정 패키지로 검증하고 과거 IAP 예제의 콜백을 혼용하지 않는다. [S07]

**중요:** Nakama 영수증 검증의 `seenBefore=true`만 보고 ‘이미 아이템을 지급했다’고 결론 내리지 않는다. 검증 저장 후 실제 지급 전에 프로세스가 죽을 수 있다. `purchase_grant`가 GRANTED인지 별도로 확인한다. VALIDATED이고 미지급이면 같은 거래로 지급을 완료한다. 이미 GRANTED이면 이전 성공 응답을 반환한다. 구매 검증 자체와 게임 아이템 지급 사이의 장애를 이 방식으로 복구한다.

구매 기록은 store+앱+transaction 또는 purchase token으로 전역 유일한 키를 만든다. 서버 권한 객체로 최초 소유 계정을 묶는다. 같은 영수증을 다른 계정에 제출하면 자동 이전하지 않는다. 복원 가능한 영구 광고 제거·패스·외형은 로그인 계정과 스토어 검증을 통해 복구한다. 기간제 소비 상품의 과거 지급분은 게임 원장에서 확인한다. 사용자가 산 화폐를 기간 만료 처리하지 않는다. [S08, S09]

환불·취소 알림은 서명 검증, 순서 뒤바뀜·중복·오래된 메시지 검증 후 적용한다. 권한 상품은 해당 권한을 철회한다. 재화 상품은 구매 원장에서 미소비 수량을 확인해 회수하며 이미 소비돼 모자라면 Wallet을 음수로 덮어쓰지 않고 별도 채무/검토 상태로 관리한다. 정상적인 환불 권리를 막거나 자동으로 영구 정지하지 않는다. 이미 강화에 사용한 물품 때문에 진행 데이터를 무차별 되돌리지 않고 고객지원 정책을 적용한다. 재검증·알림 누락 조회 작업도 운영 항목에 넣는다.

## 11. 광고 검증

AdMob SSV 엔드포인트는 공개될 수 있지만, payload 서명·공개키·transaction ID·nonce·사용자·광고 단위·보상 타입을 모두 확인한다. canonical query 처리·URL decoding·서명 알고리즘은 공급사 규격대로 테스트하며 원문을 임의 재조합해서 검증하지 않는다. 검증 성공 이벤트는 `ad_grant`에 create-only 저장하고 게임 보상은 일반 경제 트랜잭션으로 적용한다. [S10]

광고 준비 상태는 PREPARED → VERIFIED → GRANTED이며 CANCELLED/EXPIRED를 별도로 둔다. 준비 nonce의 광고 시작 유효시간은 10분, 실제 완료된 광고의 서버 콜백 대기 유예는 24시간이다. 준비 시 일일 슬롯을 예약하고 no-fill/취소를 확인한 명령은 슬롯을 해제하되, 이후 유효한 지연 콜백은 동일 source marker로 복구 큐에서 한 번만 처리한다. 부정 재사용을 막기 위해 해제된 nonce로 새 광고 시작을 승인하지 않는다. 광고 공급사 증빙이 있는 지연 완료는 사용자의 보상을 누락시키지 않는 방향으로 검토·보상하고, 과거 날짜 슬롯에 귀속한다. 날짜를 넘겼다고 새 날짜 횟수를 차감하지 않는다.

광고 제거 계정의 `ad_claim`은 SSV 대신 서버 entitlement를 확인한다. 이후 문맥·기간·횟수·중복 조건은 광고 시청과 같다. 제거 상품 구매 완료와 광고 콜백이 동시에 와도 같은 placement/context 보상이 중복되지 않게 공통 claim marker를 쓴다. 소환·아이템 드롭은 광고 SDK에서 직접 Wallet을 수정할 수 없다.

## 12. 시간·동시 접속·재시도

모든 저장 시각은 UTC, 일일 UI는 KST 오전 5시다. 일일 날짜 키는 KST 로컬시각에서 5시간을 뺀 날짜다. 예를 들어 2026-09-27 04:59 KST는 9월26일 키, 05:00은 9월27일 키다. 주간 키는 같은 보정 시각의 월요일 기준이다. 클라이언트 시간·타임존·날짜 변경으로 일일 보상을 초기화하지 않는다.

동일 계정은 활성 경제 세션 1개다. 새 기기 접속을 확정하면 `active_device_epoch`를 증가시키고 이전 기기의 경제 쓰기를 거절한다. 단순 앱 재실행은 유효한 세션 복구 경로를 우선한다. 오프라인 보상 커서는 계정 단위이며 기기마다 따로 두지 않는다. 새 기기에서 로그인할 때 진행 중 도전도 서버에서 복구한다.

일반 읽기 재시도는 지수 backoff+jitter로 하며, 쓰기는 반드시 같은 request_id/동일 payload를 재사용한다. 결제 네이티브 구매창을 네트워크 재시도 로직으로 반복 실행하지 않는다. 취소 토큰은 씬·화면 수명에 연결하되 서버에 이미 접수된 경제 명령의 취소가 롤백을 뜻한다고 해석하지 않는다. 타임아웃 후에는 요청 결과를 조회하거나 동일 ID로 재요청한다. Nakama Unity SDK의 인증·세션·재시도 동작을 고정 SDK로 검증한다. [S03]

토큰은 iOS Keychain/Android Keystore 기반 보안 저장소를 사용하고, PlayerPrefs에는 음량·FPS 같은 비민감 설정만 둔다. 설치 식별자는 무작위 생성하며 하드웨어 개인정보를 불필요하게 수집하지 않는다. 모든 트래픽은 HTTPS/TLS. 인증·DB·Apple·Google·SSV 비밀키는 서버 secret으로만 관리한다.

## 13. 콘텐츠 테이블과 배포

`data/*.json`이 이번 초기 데이터 패키지의 기계 판독본이다. CSV와 엑셀은 검토·편집 편의를 위한 동일 출발점이며 어느 하나를 편집한 뒤 자동으로 다른 파일도 바뀐다고 가정하지 않는다. 운영 개발에서는 단일 편집 원천을 선정하고 검증/변환 빌드로 client/server JSON을 동시에 생성한다. 이 패키지에서는 JSON을 기준으로 하고 `tools/validate_data.py`가 정적 검증을 수행한다.

정수 의미: `_bp`=10000당 비율, `_ms`=밀리초, `_mm`=위치, `_milli`=1000당 단위, `_weight`는 확률 가중치. JSON 금액 문자열은 빈칸/음수/실수/지수 표기를 허용하지 않는다. 다음 등급이 없으면 `next_id`는 빈 문자열, 사용되지 않는 공격 계수는 0이다. CSV는 UTF-8 BOM으로 제공한다. ID는 한번 출시하면 재사용하지 않는다.

manifest에는 schema_version, content_version, simulation_version, min_client_build, 각 파일 SHA-256, published_at을 기록한다. 서버가 검증하지 않은 클라이언트 임의 콘텐츠 버전을 허용하지 않는다. 콘텐츠 배포 절차는 데이터 검사 → 서버 시뮬레이터 회귀 → staging 전체 기능 → 소규모 노출 → 공개 version 전환이다. 변경은 원자적으로 manifest를 바꾸고, 진행 중 challenge는 옛 버전을 유지한다.

확률 테이블은 일반 밸런스 파일과 승인 절차를 분리한다. 서버 추첨·클라이언트 확률창·서비스 웹 안내가 동일 버전에서 생성돼야 한다. 실제 확률 변경은 공지·법률 검토·이전 버전 기록을 거친다. 유료 상품 번들은 구매 당시 catalog_version을 구매 기록에 남겨 변경 후 복원 시 다른 보상을 주지 않게 한다.

## 14. 저장 마이그레이션과 배포 운영

Nakama 스키마 마이그레이션은 공식 도구로 실행한다. 게임 JSON은 각 객체의 schema_version에 따라 read-migrate-write하고, 재시작·반복 실행해도 안전한 함수로 만든다. DB 마이그레이션을 모든 replica가 동시에 무작정 실행하지 않으며 배포 단계에서 한 번 통제한다. 게임 데이터 마이그레이션 중에도 구매 원장·지급 마커를 삭제하지 않는다.

dev/staging/prod는 DB·스토어 sandbox·광고 test ID·secret·도메인을 분리한다. 운영 DB와 Nakama Console은 공개 인터넷 포트를 열지 않고 사설망/VPN·접근제어 뒤에 둔다. 개발 compose의 기본 비밀번호·server key를 운영에 쓰지 않는다. 이미지 digest, git commit, content_version, schema_version을 배포 기록에 남긴다.

백업은 PostgreSQL 자동 백업과 시점 복구가 가능한 구성으로 운영하고, 목표 RPO 15분 이하·RTO 2시간 이하는 내부 초기 목표로 둔다. 실제 운영 서비스의 보장이라고 주장하지 않는다. 복원 연습에서는 계정 상태뿐 아니라 결제 외부 증빙과 지급 원장의 불일치를 재조정한다. 백업 시점 이후 실제 결제를 했던 계정의 지급이 사라질 수 있으므로 검증 재조회·grant 재구성 절차가 필요하다.

배포 롤백은 앱/서버 코드, 콘텐츠 manifest, JSON schema의 호환성 범위를 나눠 처리한다. 이미 지급한 아이템과 경제 변경을 git rollback만으로 되돌리지 않는다. 심각한 오류는 해당 소환/상품/광고 기능을 즉시 중지하고 거래 구간을 특정해 보상·회수 계획을 승인한다. 앱에 신버전이 설치되기 전에도 서버 kill switch가 작동해야 한다.

## 15. 성능 예산과 모니터링

저사양 모드 30fps, 표준 모드 60fps를 목표로 한다. 대표 실기기 3등급을 선정하고 OS·메모리·발열 상태를 기록한다. 목표 초기 다운로드 200MB 이하, 플레이 중 메모리 500MB 안팎 이하는 첫 예산이며 실제 아트/SDK 포함 빌드에서 재측정한다. 매 프레임 GC 할당 0을 전투 루프 목표로 두고, 오브젝트 풀로 주인공·몹·피해 숫자·VFX를 재사용한다.

논리 몬스터 최대 40, 표시 피해 숫자 40개, 동시 VFX 24개, 월드 음원 16개. 장비 목록·우편은 가상화하고 모든 패널을 활성 상태로 두지 않는다. 지역 전환 시 이전 지역 에셋 참조를 해제한다. 고급 광폭 이펙트는 저사양에서 입자 수와 잔상 수를 줄이되 서버 판정·공격속도는 바꾸지 않는다.

부하 검증의 초기 시나리오는 동시 활성 1000계정, 10초 heartbeat 약100 RPS에 강화·소환·결제 혼합을 더한다. 이는 지원 성능 수치가 아니라 시험 부하다. 일반 RPC p95 300ms, challenge_start p95 1000ms, 오류율 0.5% 미만을 가설로 측정하고 CPU·DB pool·lock wait·저장 객체 크기를 함께 본다. 느리다고 보스 검증을 클라이언트에 위임하지 않는다.

대시보드에는 API 지연/오류, 활성 사용자, 접속·인증 실패, DB 사용량/연결/잠금, CAS 충돌, 경제 차감 실패, 중복 방지 발생, 구매 VALIDATED 미지급, 광고 VERIFIED 미지급, outbox 적체, 콘텐츠 mismatch, crash/ANR, 재화 생성/소비를 둔다. 경고 임계값은 운영 부하에 맞춰 조정한다. 매출은 스토어 정산·환불을 반영해 별도 집계하고 검증 이벤트만으로 실수령 매출이라고 하지 않는다.

## 16. 구현 인수 조건

새 계정 생성부터 첫 보스·첫 강화·재접속·중복 요청·다중 기기·첫 결제 복원까지 실제 staging에서 연결돼야 수직 단면을 통과한다. 프로토타입 로컬 세이브와 운영 세이브를 혼용하지 않는다. 500개 stage row가 있다는 이유만으로 500스테이지가 검증됐다고 하지 않는다. 1/20/100/200/300/400/500과 각 해금 경계, 각 보스 패턴, 최고 스탯, 유료·무결제 시나리오를 실제 서버 전투로 통과시켜야 한다.

## 17. 상한 초과 확정 보상

유료·최초·우편 보상이 Wallet 상한을 넘으면 지급권을 pending_grant에 보존하고 source claim과 함께 commit한다. 이미 보존한 지급권도 영속 지급으로 기록하되 UI에 잔여 수령 대기를 표시한다. bootstrap 및 다음 재화 소비 후 가용 한도만큼 지급하고 잔여량·지갑·operation을 원자 갱신한다. 무료 지속 파밍만 상한에서 증가를 멈춘다. 구매 전 예상 초과는 UI에서 차단하지만 이미 발생한 정상 결제 복구는 막지 않는다.

# 구현 작업 순서와 완료 기준

## 1. 진행 원칙

순서는 의존성을 만족하는 단일 작업자 기준으로 번호를 붙였다. 팀 작업은 선행 산출물의 인터페이스가 고정된 뒤 아트·UI·QA를 병렬로 진행할 수 있다. P0는 보안·데이터 손실·진행 차단 위험이 높은 항목, P1도 출시 범위에 포함되는 항목이다. P1을 자동으로 다음 업데이트로 넘기지 않는다.

작업 상태는 미착수 → 진행중 → 검증중 → 완료, 의존성 또는 외부 조건이 막히면 보류다. 완료는 코드 작성이 아니라 해당 행의 검수 조건 통과와 증빙 링크 등록이다. 이 문서가 작성되었다는 이유로 게임 구현 항목을 완료로 표시하지 않았다.

## 4. 첫 플레이 검증의 정확한 범위

첫 수직 단면은 지역 1개, 임시 바바리안 1명, 무기 3계열, 일반 몬스터 3종, 보스 1종, 스킬 3개로 만든다. 로그인 → 자동사냥 → 분노 → 골드 강화 → 무기 교체 → 보스 성공/실패 → 종료 → 재접속까지 연결한다. 전체 500스테이지의 아트를 먼저 만들거나 상점 UI부터 완성하지 않는다.

첫 통과 기준은 10분 동안 개발자 콘솔 없이 플레이할 수 있고, 강화·무기 교체로 처치 양상이 달라지며, 앱을 종료해도 진행과 재화가 보존되는 것이다. 이 단계에서 재미가 부족하면 공격 주기·범위·스폰 밀도·광폭 타이밍을 수정한다. 복잡한 성장 메뉴 추가로 전투의 문제를 덮지 않는다.

## 5. 역할별 책임

클라이언트는 입력·화면·예측·재생·플랫폼 SDK를 맡는다. 서버는 검증·시간·재화·진행·실제 결과·지급 복구를 맡는다. 기획은 단일 콘텐츠 데이터와 목표·실측 비교를 관리한다. 아트는 manifest와 포즈·소켓·해상도를 지킨다. QA는 기능·보안·복원·실기기·스토어 테스트를 실행한다. 한 사람이 모든 역할을 해도 이 경계는 유지한다.

## 6. ‘출시 완료’ 판정

P12까지 모든 P0·P1 구현과 필수 테스트가 완료되고, 치명적 결함이 없고, 신규 계정부터 본편 완주 및 복귀·결제·복원·문의까지 동작해야 한다. 데이터 정적 검사를 통과한 것만으로 출시 완료라고 부르지 않는다. 외부 서비스 등록값·심의·법률 확인·실기기 성능·실결제 검증은 반드시 별도 증빙을 남긴다.

# 콘텐츠·경제 데이터 사용 명세

## 1. 원천과 버전

`data/*.json`은 이번 패키지의 정식 초기 데이터다. CSV와 엑셀은 검토·작업 관리용 사본이다. 숫자를 고친 뒤 다른 표현과 런타임 입력을 제각각으로 방치하지 않는다. 이번 패키지의 `tools/validate_data.py`는 정적 검증 도구이며 Unity Importer나 Nakama 런타임 로더 구현을 대신하지 않는다.

정수량이 커질 수 있는 HP·공격력·골드는 JSON에서 10진 문자열로 저장한다. 런타임 로더는 검증 후 Int64로 읽는다. 계수는 10000=100%의 bp, 좌표는 mm, 시간은 ms 또는 필드명에 명시된 초를 사용한다. null 비용은 해당 레벨에서 다음 강화가 없다는 뜻이다. 보상과 비용의 음수 입력은 금지한다. `schema_version=1`, `content_version=1.0.0-seed.1`을 기준으로 한다.

무기·방어구·스킬·유물·퀘스트 ID는 출시 이후 같은 의미를 유지한다. 삭제할 항목도 ID를 다른 아이템에 재사용하지 않는다. `asset_key`는 제작할 리소스의 주소이지 이미 포함된 아트 파일 경로가 아니다.

## 9. 반복 지급 보석과 일회성 보석

일일 상자200 + 주간상자700÷7 + 출석210÷7 = 조건을 모두 충족한 장기 평균 330보석/일이다. 스테이지 최초 보상·탑·초보 과제·패스·30일 보급권은 이 값에 포함되지 않는다. 이 산술값은 실사용자 수령량이나 매출 예측이 아니다. 무료 소환 3종 각1회는 보석 지급량과 별개다.

## 10. 전량 표와 수정 방법

500스테이지와 3001개 성장 레벨을 본문에 모두 복제하지 않는다. CSV/JSON과 엑셀에서 확인한다. 규칙 수정은 기획서 → JSON → 검증 → 클라이언트/서버 콘텐츠 해시 일치 → 회귀 테스트 순서다. 운영 데이터를 엑셀만 고쳐 서버에 수동 반영하지 않는다.

## 11. 산출물과 실제 리소스의 구분

`asset_manifest`의 모든 상태는 미제작이다. 모델·스프라이트·음원·Unity Prefab·Go 모듈이 이 패키지에 완성된 형태로 들어 있지 않다. 실행 가능한 것은 Python 정적 검증기이며 게임 엔진과 서버는 작업표에 따라 구현해야 한다.

# 검증 계획과 출시 게이트

## 1. 검증 범위 구분

이 패키지에서 실행하는 검증은 **데이터 정적 검사**다. 실제 실행 결과는 `qa/static_validation_report.json`에 기록한다. 아래의 Unity/Nakama/결제/실기기 QA는 **실행 예정 계획**이며 모두 미실행으로 시작한다. 기획상의 수치가 존재한다는 사실은 전투 재미, 장기 성장 속도, 서버 수용량을 검증했다는 뜻이 아니다.

## 2. 데이터 정적 검사 실행

Python 3.9 이상 환경에서 저장소 루트에서 실행한다. 외부 패키지 없이 동작한다.

```bash
python tools/validate_data.py
```

종료코드0은 이 검사기의 정적 조건을 통과했다는 뜻이고 출시 승인이라는 뜻이 아니다. 종료코드1은 조건 불일치,2는 읽기/파싱 등 실행 오류다. 콘텐츠를 바꾼 뒤 검사 항목이 새 설계와 맞는지도 함께 검토한다.

## 3. 구현 단계별 게이트

순수 전투 코어는 고정 seed 최소10000개에서 C#·Go의 동일 종료 tick·HP·결과·이벤트 해시를 확인한다. 같은 결과만 대충 맞추지 말고 틱별 차이 위치를 찾는다. 서로 다른 CPU·IL2CPP 빌드에서도 RNG와 정수 나눗셈을 검사한다.

경제는 중복·순서 역전·재시도·CAS 충돌·프로세스 중단을 장애 주입으로 테스트한다. 결제는 검증 전/후, 지급 전/후, 응답 전/후 경계를 분리한다. 광고는 서명·nonce·유저·배너·일자·콜백 중복을 검사한다.

본편은 무과금, 무과금+광고3회, 무과금+광고7회, 보급권, 선택 패키지의 다섯 경로를 비교한다. 하루 접속 시간과 접속 횟수를 입력으로 고정한다. 매출·잔존율·ARPPU는 실제 데이터가 없는 상태에서 보장하지 않는다.

## 4. 밸런스 측정 기록

기본 플레이 모델은 하루2회 접속, 회당15분, 방치시간은 실제 간격, 무과금·광고0회부터 시작한다. 초기30분은 별도 녹화와 이벤트로 측정한다. 점검 구간은 stage1/3/8/10/20/30/60/100/150/220/300/350/400/500이다.

각 지점에서 계열,스탯레벨,슬롯강화,스킬조합,분노가동률,일반분당처치,골드/분,보스클리어초,실패이유,다음목표까지필요시간을 기록한다. 도끼·대검·망치는 같은 지출과 같은 유물·승급 상태로 비교한다. 무한 재도전의 평균이 아니라 seed 분포의 성공률도 기록한다.

목표 가설은30분 첫승급,1일40~60,7일120~180,30일약300,45~75일500이다. 실제 시뮬레이터와 플레이테스트가 이 값을 벗어나면 데이터 곡선을 수정한다. 목표에 억지로 맞추기 위한 숨은 과금별 난이도나 개인별 확률은 사용하지 않는다.

## 5. 성능·복원 목표

Android/iOS 대상 저사양 실기기를 팀에서 지정한다. 30분 최대 몬스터·스킬 상태에서 fps분포·최대메모리·발열·배터리·GC를 기록한다. 초기 메모리500MB 안팎,초기다운로드200MB 이하는 내부 예산이며 이미 달성한 실측값이 아니다.

부하는1000가상동접×10초heartbeat=정상 heartbeat약100요청/초에 경제·로그인·도전을 섞어 시작한다. p95 일반RPC300ms,도전준비1초는 목표다. 하드웨어·PostgreSQL설정·시뮬레이션CPU비용에 따라 조정한다. 이 문서가1000동접 운영 가능성을 보증하지 않는다.

백업은 실제 별도 환경에서 복원한다. RPO15분/RTO2시간은 운영 목표이며 실제 복원 실험 결과를 기록해야 한다. 복구 후 외부 결제 원장과 내부 grant 원장을 대사해 이미 유효하게 구매한 상품을 잃지 않도록 한다.

기대 결과: 각계열쓰임존재;하나가모든상황지배하면계수조정

### Q089 · 외부 등록

분류: 출시 / 우선순위: P0 / 관련 단계: P12 / 상태: 미실행

### Q090 · 실결제 끝까지

## 7. 출시 승인 체크

모든 P0와 출시 필수 P1 검증, 데이터 마이그레이션·백업 복구·토큰 탈취 방어·원장 복구를 통과한다. 실제 사업자 정보,약관,개인정보 안내,확률 안내,고객 문의,계정 삭제 경로,스토어 상품·광고 설정이 채워져 있어야 한다. 게임 이용등급·국내 확률형 표시·결제/환불·광고 동의 등은 최신 규정으로 검토한다. [S08,S09,S10,S13]

출시 후보의 콘텐츠 해시·앱 빌드·서버 이미지 digest·DB 마이그레이션 버전을 함께 기록한다. 검수 도중 데이터를 바꿨다면 영향을 받은 케이스를 다시 실행한다. 본편500완주 이후에도 깨진 빈 화면이나501스테이지 무한 접근이 없어야 한다.

# 상태 전이·전투 기하·인터페이스 세부 규칙

이 문서는 본문에서 생략하기 쉬운 구현 경계를 닫는다. 기존 게임기획서의 규칙을 대체하는 새 콘텐츠가 아니라 같은 1.0 규칙의 구체화다.

## 1. 메인 상태 전이

BOOTSTRAP → FARMING이 기본 흐름이다. CHALLENGE_PREPARING은 서버 요청이 승인되기 전 상태다. 승인되면 CHALLENGE_PLAYING, 종료 시각 이후 RESULT_PENDING, 서버 결과를 받으면 RESULT_CONFIRMED, 마지막으로 FARMING으로 돌아간다. 어떤 네트워크 응답도 유효한 challenge_id와 device_epoch가 다르면 현재 화면 상태를 뒤집지 못한다.

네트워크가 잠깐 끊기면 마지막 확정 상태를 기준으로 최대 lease 범위만 예측한다. lease를 넘으면 ‘연결 확인 중’ 상태로 전투 경제 표시를 정지하고 재접속을 기다린다. 앱이 백그라운드로 가면 클라이언트 프레임 처리는 중지한다. 서버 시간 정산은 별도다. 전면 팝업이나 프레임 정지가 서버 시간의 정지가 아니다.

RESULT_CONFIRMED에 들어가면 성공/실패를 한 번만 재생한다. UI 애니메이션을 닫아도 수령된 보상은 사라지지 않는다. 재접속 시 이미 지급된 결과를 다시 보여 줄 수 있지만 재지급하지 않는다.

## 2. 논리 전장의 기본값

일반사냥 시작은 주인공 X=0, 적 0마리, 첫 생성 tick=0이다. 생성 위치는 주인공 현재 위치 기준 좌우 중 균등 선택, 거리 8000~10000mm의 50mm 단위 균등 선택이다. 카메라 화면비·줌·해상도는 생성 위치에 영향을 주지 않는다. 몬스터 유형은 해당 지역의 55% 군집/25% 중갑/20% 원거리 비중으로 뽑는다.

주인공과 적의 표시 중심이 논리 위치다. 충돌체 반지름을 사거리에서 임의로 빼지 않는다. 이동 tick마다 speed_mm_per_second × 50 ÷ 1000을 적용하고, 분수 잔량이 생기면 엔티티에 보관한다. 정확히 사거리 경계에 있으면 타격 가능하다. 적끼리 밀지 않으며, 여러 적이 같은 X에 있어도 ID로 분리한다.

도전 시작은 주인공 X=0, 보스 X=6000, 보스 양옆 소환물이 필요하면 보스 X±1500이다. 몬스터의 최초 기본공격은 생성 후 그 몬스터의 기본 공격주기만큼 지난 뒤부터 가능하다. 주인공의 최초 평타와 스킬은 시작부터 준비 상태다. 보스의 기본 공격 간격은 2000ms, 근접 사거리는 2000mm다. 보스도 사거리 밖이면 기본 1600mm/초로 접근한다. 일반 적은 데이터의 이동·공격거리 값을 쓴다.

골드 던전은 주인공 X=0, 첫 tick부터 초당3마리로 생성하며 최대20마리다. 첫 30마리 누적 처치에 성공한다. 도전용 소환 몬스터가 있는 모드는 기본 스테이지의 보상 없는 몬스터 스탯을 쓰고, 재화·도감·과제·처치 분노를 생성하지 않는다.

## 3. 공격과 애니메이션

평타의 논리 피해는 공격 예약 tick에 발생한다. 1.0에는 평타 투사체 비행시간·정면 패링·정밀 히트 프레임이 없다. 클라이언트의 타격 포즈와 섬광을 해당 논리 이벤트에 맞춘다. 후딜은 다음 평타 주기가 담당한다. 애니메이션 길이를 바꿔도 DPS가 달라지지 않아야 한다.

회전베기는 시전 시작 위치에 고정, 첫 타격 즉시 이후100ms 간격으로 총6타다. 시전 잠금250ms 이후 이동을 재개할 수 있으나 이미 예약한 회전 중심은 움직이지 않는다. 지면분쇄는 시전 시작 위치·바라보는 방향을 고정하고 즉시/200/400ms에 전방 같은 범위를 타격한다. 투척도끼는 즉시 전방 범위 판정이며 도끼가 돌아오는 연출은 추가 피해를 주지 않는다.

도약강타는 가장 가까운 타깃이 8000mm 이내일 때 타깃 방향으로 도약한다. 도약 착지 논리 위치는 타깃으로부터 시작 방향 쪽 900mm 앞이며, 이동 및 타격은 시작 tick에 확정한다. 점프 높이·체공은 시각 연출이고 무적이 아니다. 착지 위치에서 주변 반경2200mm의 최대8명을 타격한다. 타깃이 없으면 시전하지 않는다.

야만돌진은 시전 방향으로 최대4000mm 이동한다. 첫 타격은 현재 위치, 이후150/300/450ms에 각각 누적 이동 거리의 1/3, 2/3, 전체 위치에서 전방1000mm 범위를 판정한다. 대상 수는 타격마다 최대8, 같은 적의 다중 타격을 허용한다. 시전450ms 동안 일반 이동 AI는 중지하고 끝나면 복구한다. 장애물 충돌·무적은 없다. 데이터 range_mm=4000은 이동 경로 길이다.

피의참격은 주변2400mm 범위 직접 피해 후 살아 있는 대상에게 출혈을 부여한다. 직접 피해는 치명타 가능, 출혈은 1초마다6회다. 출혈량은 부여 순간의 공격력·레벨·피해 버킷을 고정하되 치명타 없이 계산한다. 출혈 중 광폭이 끝나도 이미 고정한 출혈 피해가 재계산되지 않는다. 선조의철퇴는 주변4000mm를 즉시 타격하고 광폭 중이 아닐 때만 분노를 추가한다.

보스 예고는 기본공격과 별개 패턴 타이머다. 보스1의 8초 패턴은8초에 예고 시작,8.8초에 피해다. 보스5의 지정시각은 예고 시작을 뜻하며 내려찍기는800ms 뒤 타격한다. 다른 방어·감속 버프는 지정 tick에 시작한다. 보스는 예고 중 기본공격·이동을 중지하고 피해 확정 후 재개한다. ‘예고’는 수동 회피를 요구하지 않으며 준비된 생존 빌드로 견디는 신호다.

## 4. 성장·세트·장착 경계

방어구 전체 보너스는 각 부위의 등급 HP 보너스에 해당 부위 슬롯 강화 배율(1+0.005×강화레벨)을 곱한 뒤 세 부위를 합한다. 그 뒤 기본 최대HP, 승급 배율, HP 가산 버킷을 적용한다. 세트 효과는 모든 장착 방어구의 최저 등급으로 결정하고 최고 충족 단계 하나만 적용한다. 빈 부위가 있으면 세트 효과는0이다.

2개 프리셋은 무기·세 방어구·스킬 순서·특성 배치를 저장한다. 장비 사용권/스킬 사용권이 없는 프리셋은 적용할 수 없다. 특성 포인트가 부족해지거나 데이터가 바뀐 프리셋도 전체 적용을 거부하고 수정 화면을 연다. 가능한 항목만 조용히 일부 적용하지 않는다. 프리셋 저장은 로컬 초안이 가능하나 계정 저장은 RPC로 확정한다.

이미 사용권이 있는 보상을 받으면 중복수+1, 사용권이 없으면 사용권=true, 중복수는 기존값 그대로다. 합성 보상도 이 규칙을 따른다. 최초 사용권 자체는 비용으로 소비하지 않는다. ‘중복5개’는 사용권 외의5개이므로 처음 보는 장비를 바로 합성하려면 총6회 획득이 필요할 수 있음을 안내한다.

## 5. 도전 중 포기·중단

포기 요청 시 서버 현재 시각이 저장된 terminal_at보다 이르면 실패/포기로 종료하고 던전 예약은 반환한다. terminal_at 이후에는 이미 정해진 결과를 확정하며 승리의 입장 횟수와 보상을 적용한다. 포기로 일일 ‘도전 종료’ 과제를 채울 수 없다. 앱 강제종료는 포기 요청으로 간주하지 않는다.

도전 중 상점 지급은 가능하지만 전투 snapshot에는 반영되지 않는다. 도전 중 강화·장착·특성 재설정·사냥터 이동은 CHALLENGE_ACTIVE다. 도전 시작 전에 파밍 미정산분을 먼저 확정한다. 도전 구간은 일반사냥 정산에서 제외한다.

## 6. 방치 정산 예외

방치에서 재화와 처치 수를 모두 70% 효율로 산정한다. 재화만70%, 처치 수100%로 도감을 빨리 완성하는 별도 규칙은 없다. 골드 버프는 골드 산정만 바꾸며 광석·가루·처치 수는 바꾸지 않는다. 온라인·오프라인·버프 구간을 분리하되 소수 잔량을 종류별로 이어 붙인다. 표시 반올림은 지급 정수와 분리한다.

안정 사냥터는 해당 빌드의120초 시뮬레이션에서 사망0회이고 후반90초 처치 수가1이상인 사냥터다. 일반사냥에서 자동 안정 이동이 켜져 있고120초 내3회 사망하면, 최근 검증 캐시 중 현재보다 낮은 가장 높은 안정 사냥터를 우선한다. 없으면 현재 아래 최대10개를 내림차순 검증하고, 그래도 없으면1스테이지로 이동한다. 이때 현재 구간을 먼저 정산하고 다음 보스 자격은 보존한다.

한 번의 claim으로 기본 방치 보상은 자동 지급된다. 30분 이상이면 생성하는 추가 보상 영수증은 원래 확정 자원량의50%를 기준으로 한다. 광고를 볼 때 새 강화나 새 버프 수치로 재산정하지 않는다. 영수증1개당1회이고 하루2회다. 일반사냥 보상과 방치 광고 보상은 별도 지급원으로 원장에 남긴다.

## 7. 무료 소환·상한·보상 넘침

배너별 일일 무료1회가 남아 있으면1회 또는10회 소환 모두 첫 추첨에 무료권을 먼저 사용한다. 그 뒤 해당 배너 티켓, 무료 보석, 유료 보석 순서다. 버튼을 누르기 전에 ‘무료1+티켓3+보석600’처럼 실제 조합을 표시한다. 상태가 달라져 유료 차감이 늘어나면 구요청을 거부하고 다시 확인한다. 소비 가능한 재화가 전체 수량보다 부족하면 부분 소환하지 않는다.

보석·골드 상한 초과 상태에서 재화를 소멸시키지 않는다. 무료 파밍은 상한에서 증가하지 않는다고 사전 표시하고, 유료 상품·우편·확정 일회성 보상은 지급대기 항목으로 보존한다. 해당 지급원이 다시 청구되어 이중 적용되지 않도록 pending_grant와 claim marker를 원자 저장한다. 유료 구매 UI는 예상 초과가 확인되면 구매를 막고 기존 pending 결제의 복구는 계속 지원한다. 경계 테스트는 pending_grant 일부 해소와 재접속을 포함한다.

## 8. RPC 예시

요청 금액·공격력·승리 여부를 받지 않는다. 아래는 계약 예시이지 실제 Nakama SDK 호출 코드가 아니다.

```json
{
  "request_id": "f37c8afe-43f6-41f3-a203-c4b6d7ca7868",
  "client_build": "1.0.0",
  "content_version": "1.0.0-seed.1",
  "expected_revision": 42,
  "device_epoch": 3,
  "payload": {"stat_id":"ATK","count":10}
}
```

응답은 실제 commit 결과의 revision과 delta다. UI는 요청 전 추정한 비용을 결과로 확정하지 않는다.

```json
{
  "ok": true,
  "code": "OK",
  "server_time_ms": "1790500000000",
  "state_revision": 43,
  "content_version": "1.0.0-seed.1",
  "delta": {
    "wallet_delta": {"gold":"-160"},
    "growth":{"ATK":10}
  },
  "result":{"applied_count":10},
  "retryable":false
}
```

위 비용160은 ATK 레벨0에서10까지의 초기 데이터 합계다. 실제 비용은 요청 당시 시작 레벨의 성장 데이터 합계로 계산한다. request_id와 payload_hash를 묶고, 서버가 운영 중인 account revision과 content version을 검증한다.

bootstrap에는 server_time_ms, active_device_epoch, state_revision, content_version, wallet, progress, growth, equipment, skills, talents, artifacts, codex, daily, entitlements, farm_snapshot, pending_challenge, newly_settled_receipts, service_flags를 포함한다. 비공개 미래 도전 결과·검증 영수증 원문·관리자 메모는 포함하지 않는다.

## 9. 로그·이벤트 필수 필드

경제 이벤트에는 source_type, source_id, request_id, user_id, before/after_revision, currency, delta, balance_after, content_version, server_time을 기록한다. 상품은 product_id, platform, transaction_hash, verified/granted/confirmed 상태를 추가한다. 광고는 placement, nonce, transaction_hash, 검증/지급 상태를 추가한다. 개인정보·영수증 원문·인증 토큰은 일반 분석 로그에 넣지 않는다.

콘텐츠 실험을 도입하기 전까지 유저별 확률·가격·보스 HP A/B는 하지 않는다. 1.0에서는 전체 동일 content version으로 측정한다. 확률이나 상품 변경은 공지·심사·운영 검토와 데이터 버전 변경이 필요한 별도 배포다.

## 2. 버전·법률 확인 경계

Unity6.3LTS라는 계열은 고정했지만 패치별 호환 조합은 P01에서 실제 빌드로 잠근다. Nakama Docker의 예시 태그를 최신 보안 패치라는 뜻으로 사용하지 않는다. PostgreSQL의 지원 중인 메이저와 패치를 실제 배포 시점에 확인한다. Go pluginbuilder와 서버 이미지는 같은 태그·플랫폼·공유 의존성 기준으로 고정한다.

Nakama의 영수증 검증과 게임 아이템 지급은 같은 사건이 아니다. ‘이미 검증한 영수증’과 ‘게임 지급 완료’ 상태를 구분해 복원한다. Unity IAP5/StoreKit2JWS를 쓸 때는 도입한 Nakama 버전의 지원 여부를 다시 확인한다.

국내 확률형 아이템 안내 자료 S13은 공개 안내문을 찾는 출발점이다. 2024년 안내만으로 2026년 이후 적용 법령 전체,표시 예외,제재,심의 요건이 충족됐다고 판단하지 않는다. 출시 국가·이용등급·결제·환불·개인정보·광고 동의·확률 공개는 출시 시점의 최신 자료 및 필요한 전문가 검토로 확인한다. 이 문서는 법률 의견서가 아니다.
